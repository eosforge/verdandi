# Star/Planet 推流传输对照详细报告

日期: 2026-09-10. 对照版本: v3. 范围: Rust Star/Star 与 Planet/Star 传输原型, 不包含 SDK.

后续决定: 维护者已接受实测开销并选择 gRPC. 下文保留 v3 原始测量及当时条件判断;
它不再决定当前传输, 也不证明新版账号认证. 参见 [v4 实现](grpc-implementation.md).


## 1. 结论与使用边界

结论: gRPC 长期双向流能够承载当前模拟的主要推流负载, 但本次不能证明转换后没有性能损失.
在全部完成的 Ubuntu 本机场景中, 每秒 6 万次 Catalog 源更新向四端广播时, 两者交付吞吐都接近每秒 24 万条;
gRPC 更新 P99 比批量 TCP 高约 24%～29%, 进程 CPU 秒高约 12%～22%.
Windows 本机和跨机高负载还存在未完成样本, 不能用成功轮次的吞吐掩盖它们.

因此本轮不将正式 Star/Planet 骨架切换到 gRPC. 保留当前 TCP + Protobuf 传输和隔离原型,
不引入两套生产传输后端. gRPC 的接口生成与框架生命周期管理仍有价值; 是否值得接受实测开销,
需要结合实际负载、延迟目标和维护成本另行判断, 不能从本次结果推出 gRPC 不适合该系统.
这是对维护者“性能不拖慢再转换”条件的审核结果, 不是永久排除 gRPC 的设计决策.

每个环境包含 22 个场景 × 2 种传输 × 5 轮, 共 220 次; 三组总计 660 次. 两种传输交错先后运行, 各环境串行执行.
每次源负载计划持续 2 秒, 然后排空并核对完成水位及各接收端全表 SHA-256. 完成不等于达到提供速率; 吞吐会包含排空前的落后时间.

## 2. 模型与指标定义

- 同一个发布器、字符串键 HashMap、版本递增和广播调度器供 TCP/gRPC 共用. 数据更新生成新内容, 广播时共享不可变 Bytes.
- Registry 为 100/1000/10000/100000 条独立的 128 B 注册数据. Catalog 固定 1000 个键, 专项更新体为 64/256/1024 B.
- 初始缓存预置在 Join 屏障前, 衡量暖缓存增量. Registry 条数不是连接数; 四个接收端是一个测试进程内四个独立缓存/会话, 不冒充四台真实机器.
- Registry 专项更新既有键的值, 不创建/删除大量键, 不包含扩容重哈希. Catalog 内容是完整字节值, 不包含 JSON/MessagePack 解析或 Patch 合并.
- 正式 push 矩阵没有额外独立的稳定负载预热阶段; 缓存构造和连接/Join 完成后开始计量. 旧 Echo 的 250 ms 预热不适用于这里.
- 混合源流量为 25% Registry + 75% Catalog, 每 500 ms 穿插四个 16 KiB 合成快照片段. Catalog 专项没有快照片段.
- 每端另有 20 次控制探测/s 和 5 次小发布/s. 每 128 条已应用更新反馈一次累计水位, 约 0.8% 反向消息, 没有逐条 ACK.
- 更新延迟从计划发布时间开始, 到发布端收到应用确认结束, 使用发布端同一单调时钟. 它包含发压器落后、排队、传输、接收应用及确认返程, 不是跨机时钟相减得到的单向延迟.
- 每轮更新 P95/P99 取各接收端中最差的分位数, 表格再取五轮中位数. 不对分位数求平均. 原始 JSON 保留逐端统计、丢弃采样数和过期时间戳数.
- 原始 p99_ms 是控制 RTT; 本报告更新尾延迟使用 update_p95_ms/update_p99_ms. 两者不能互换.
- 吞吐为所有接收端合计的更新交付量, 单位千条/s. 源速率 × 接收端数是背景提供负载; 少量反向发布会增加交付条数.
- 直方图桶宽 0.1 ms. 低速两秒样本每端只有约 31 次水位采样, 其 P99 接近抽样最大值, 不足以给出生产 SLA 或高置信度极端分位数.

TCP 推流把至多 16 个已经就绪的完整帧合并写入并 flush, 不为了凑批次等待; Tonic 可合并 HTTP/2 输出. 两者都及时刷新空闲前的最后一条消息. 这是两个具体实现的比较, 不能推断协议的理论极限.
两端均为 release 构建, 每进程两个 Tokio 工作线程, TLS 1.3 双向验证、签名准入和 TLS exporter 证明. 应用队列 16 条, 控制队列 8 条, 共享广播环 512 条, 消息上限 32 KiB, gRPC 流/连接窗口均 1 MiB.

## 6. 资源

CPU 是两端进程 CPU 秒的中位数, 不是墙钟时间. 接收进程包含初始缓存构建和最终摘要计算; 本机发布进程取 ready 后增量, 跨机发布进程包含启动. 因此不能直接当作稳态每消息 CPU 成本.
RSS 为每进程 20 ms 采样峰值的跨轮最大值, 含初始化和摘要阶段. 接收进程内包含全部四份接收端缓存. 未测逐消息分配次数、纯线上字节或持久化 I/O.

## 7. 测试、失败与清理

- 两端正式 Star/Planet 工作区均通过 39 项测试, 传输原型均通过 14 项测试, 并通过 Clippy -D warnings / rustfmt 检查. 覆盖双角色、完整数据和半关闭、会话证明重放、缺失/超大证明、消息上限、取消、慢读、停止活跃连接、截断帧、认证期限和非法上游角色.
- 新增共享发布源连续版本/缓存收敛、广播环溢出显式失败, 以及 10 万条 Registry 下的小 Catalog 推流和 200 ms 消费暂停可观测性验证.
- 共用 Python 测试: Windows 24 项通过; Linux 23 项通过、1 项 Windows 文件共享语义测试跳过. 修复 Windows 短暂文件读取导致结果原子替换失败, 只做至多两秒重试, 不截断旧报告. 清理单元测试固定前置内存条件, 不再被 VM 的瞬时空闲内存误导.
- 每次本机测试使用 Windows Job / POSIX 进程组拥有进程, 正常、失败、超时都会回收. 跨机由远端拥有者响应停止/SSH EOF, 并有独立服务寿命上限.
- 预实验对比了逐帧刷新与不刷新, 后者复现了最后水位滞留超时. 正式 common/FrameWriter 同样缺少刷新, 已补齐并加入缓冲传输/刷新期限回归. 推流对照进一步使用有界批量写入和刷新. 旧 Echo/v1/v2 数字不用于本报告结论, 全部 v3 重新测量.
- 该问题扩散到共用 Rust 写入器的 Star/Planet 及准入控制路径. Go Supervisor 直接使用 Go TLS 连接写入, 没有同样的 tokio-rustls 缓冲契约; Rust/Go/C++ SDK 的 Redis 写入由各自驱动管理, C# 复用 C++ 核心, 未发现相同的手写 TLS 写入点. 本轮未运行 SDK 测试.
- 刷新要求依据 [tokio-rustls 0.26.4 官方说明](https://docs.rs/tokio-rustls/0.26.4/tokio_rustls/). 源码指纹和两平台二进制哈希与跨机执行相互校验通过.

本机四次失败有服务端落后诊断. 跨机入口保存了客户端错误和远端清理/资源结果,
没有保存远端临时 server.log; 六次跨机失败不能一律归因为广播环溢出, 也不能都归咎于 gRPC.
这一诊断缺口是后续定位工作的限制, 原始失败没有删除或用重跑覆盖.

512 条共享环在 60000/s 下只保留约 8.5 ms 的源历史. 线程调度、流控或消费者停顿可能耗尽它.
这是当前有界队列实现需要面对的恢复边界, 不等同于 TCP/gRPC 协议容量上限.
原型将落后显式转为失败, 尚未实现生产重新同步. 扩大环可以增加容忍时间, 也会增加内存和排队;
不能仅通过扩大缓存把失败隐藏起来, 需要结合实际业务定义回压、断流和恢复规则.

## 8. 尚未测量的边界

该程序是共享业务状态的传输原型, 不是已经实现的完整 Star 网格. 未测量真实 Supervisor CAS/候选切换、持久确认、全量快照恢复、网络分区/长期重连、数小时压力、更多 Catalog 键基数、更多批量/窗口调优组合、gRPC 极限容量和真实多机全网广播. SDK 按本轮要求不在测试范围.
Ubuntu 为动态内存虚拟机; 保护依据实时可用内存, 低于 256 MiB 停止, 不把启动时的内存当作固定上限.
Windows 机器为 Xeon E5-2680 v4, 报告 28 个逻辑 CPU; Ubuntu VM 配置 6 个 CPU, 内核 7.0.0-31-generic.
本轮跨机方向固定为 Ubuntu 发布、Windows 接收, 未测反向发布; 结果不能直接换算成其他硬件的生产容量.

## 10. 结果解读与后续取舍

1. **普通负载可用.** 普通推流、16 会话扇出、50 ms 突发、200 ms 暂停和所有 Registry 基数场景,
   两端与跨机全部完成. Catalog 源速率 2000/8000/20000/s 的全部组合也完成.
   650 个完成样本没有最终积压、版本缺口、过期水位采样或跳过采样, 接收端最终缓存摘要一致.
2. **固定负载下吞吐接近不代表极限相同.** Ubuntu 的高负载两者都约为 24 万条交付/s,
   因为提供速率固定. 不能据此宣布两者峰值吞吐相同或达到生产容量上限.
3. **Linux 高负载 gRPC 的附加开销可观测.** 64/256/1024 B 的更新 P99 分别为
   TCP 3.1/4.2/6.2 ms, gRPC 3.9/5.2/8.0 ms. 同组 gRPC 进程 CPU 秒高约 12%/15%/22%.
   1 KiB 下五轮 P99 范围为 TCP 5.2～7.1 ms, gRPC 6.4～16.5 ms.
   CPU 包含启动和摘要阶段, 这是该测试过程的资源差异, 不是精确的逐消息 CPU 成本.
4. **Registry 条数没有造成暖增量吞吐明显下降.** 从 100 到 10 万条, 四端均维持约 3.2 万条交付/s,
   内存却随实际数据增加. Ubuntu 在 10 万条时发布端峰值约 36 MiB, 含四份表的接收端约 141～144 MiB.
   不能推广为冷启动、全量同步或大量注册创建/删除也无影响.
5. **慢端问题需要业务策略.** 200 ms 暂停在 2000/s 下对应约 400 次源更新, 本轮可以追回,
   更新 P99 约 189～203 ms. 这不证明 60000/s 的慢端也可恢复; 同样停顿会产生约 12000 次更新.
   更换传输不会自动解决同步窗口和恢复策略.
6. **Windows 尾延迟含源调度因素.** Windows 发布时普通更新 P99 常在十几毫秒,
   Ubuntu 发布、Windows 接收的跨机普通值却常在 2～3 ms. 由于指标从计划发布时间计时,
   不能把前者全部解释成网络或 TLS 延迟. 定时器与调度是可能因素, 本轮没有独立定量归因.
7. **gRPC 价值主要是接口与生命周期标准化.** 它可减少手写 RPC 分派、状态映射和流生命周期代码,
   但这里尚未量化完整迁移后的净代码量. Protobuf 消息生成在 TCP 路径已经存在;
   gRPC 仍不替代 Registry/Catalog 状态合并、持久化、候选换绑、慢端恢复和业务 SDK.

若后续继续迁移评估, 优先补齐跨机服务端有界错误采集, 定位上述连接失败;
再以实际部署负载和明确延迟/CPU 预算进行更长的稳定负载试验, 保持 TCP/gRPC 相同业务语义.
只有这些证据满足所选预算, 才有依据把隔离原型变成正式 Star/Planet 传输.
当前保留 TCP 的成本是继续维护分帧与连接生命周期; 选择 gRPC 的成本是新增框架依赖、缓冲层和已观察到的开销.
