# gRPC 条件迁移审核与验证方案

日期: 2026-09-10. 状态: 维护者倾向在性能不拖慢的前提下转换当前骨架.
已获准将 Tonic 0.14.6 及必要传递依赖放入两端项目缓存, 隔离原型和正式 v3 推流对照已完成.
原型位于 `testkit/transport`, 当前正式服务的启动路径、传输协议和依赖清单保持原状.
维护者补充: 应模拟正常消息调度, 且绝大多数业务是推流. 因此共享发布源主动推送是
本轮主判断负载; 已完成的回声吞吐/逐条等待测试只作为辅助, 不能单独决定迁移.
当前运行契约仍是 [Star/Planet 连接规则](connection-rules.md).

实测结论见 [详细报告](grpc-benchmark-results.md): 三种环境共 660 次试验, 650 次完成、10 次未完成.
普通流量及 Catalog 源速率不超过 20000/s 的组合全部完成. Ubuntu 高负载吞吐相近,
但 gRPC P99 和 CPU 秒高于批量 TCP; Windows/跨机高负载还有失败, 跨机根因尚未确定.
本轮没有满足“转换后不拖慢”的证据条件, 因此正式骨架暂不迁移, 原型继续隔离.
这不排除以后依据实际业务预算接受 gRPC 的工程取舍.
实验另发现并修复了正式 common 控制帧的 TLS 尾部刷新问题, 详见 [专项审计](tls-flush-audit.md).

## 1. 目标与判断边界

目标是用标准的跨语言 RPC/流式接口减少长期维护的传输代码. 维护者进一步收窄本轮验证范围:
只测 Star/Star 和 Planet/Star, 不测试 SDK, 不把 Supervisor 当作性能评估目标.
Supervisor 沿用当前准入服务作为配套. 通过验证后再决定服务骨架的正式迁移, 不默认形成两套正式传输后端.
Rust 仍负责 Star/Planet, Go 仍负责 Supervisor, `cluster/common`, `cluster/star`, `cluster/planet` 所有权划分保留.

gRPC 能从 schema 生成 RPC 客户端/服务端接口, 支持双向流及 deadline/cancellation.
它不会生成 Astra 的完整业务 SDK, 也不会代替版本合并、Selector、缓存、持久确认和换绑恢复.
[官方概念](https://grpc.io/docs/what-is-grpc/core-concepts/) 支持上述传输能力;
是否能减少本项目维护成本属于需要通过原型验证的工程判断.

不能提前承诺零性能损失. 先比较同等安全和资源约束下的有效吞吐、尾延迟、CPU、分配及内存,
不默认接受 5%/10% 等未经维护者选择的性能退化预算. 可重复退化必须明确呈现.
业务 QPS、尾延迟 SLO 和最终部署规模尚未确定, 不把合成消息测试称为生产容量认证.

## 2. 迁移时应删除、保留和重审的内容

| 内容 | 迁移方向 | 边界 |
| --- | --- | --- |
| 自定义 TCP 分帧与 MessageID 分派 | 由 RPC 方法与 gRPC framing 替换 | 不把现有完整帧再塞进通用 bytes 隧道 |
| 消息类型和方法定义 | 继续由 Protobuf 维护, 增加 service/rpc 定义 | 多种流内消息使用显式 oneof 或按实际职责拆 RPC, 不一消息一条长期流 |
| 生成器 | 显式生成消息和服务接口并纳入源码 | 普通构建不下载工具、不执行 protoc、不更新锁文件 |
| RPC 生命周期 | 使用框架期限、取消和状态码 | 业务幂等、未知执行结果和持久确认仍由项目定义 |
| Star 网格与 Planet 候选 | 保留角色和拓扑所有权 | 不交给通用 round_robin 随机选择未经批准的节点 |
| 唯一活动上游与进程替代 | 保留本地 generation 和签名 epoch 约束 | HTTP/2 stream ID 不是进程身份或业务版本 |
| 保活 | 评估 HTTP/2 PING 接管传输探测 | 若还需要业务循环进展检测, 单独定义应用探测, 不能混为健康证明 |
| 认证 | 保留 mTLS、Galaxy/role/group、签名准入及进程持有证明 | 不用普通 mTLS 偷换目前的 TLS exporter 会话绑定保证 |
| 消息与队列预算 | 接入 gRPC 字节/并发窗口限制, 继续限制应用对象数量和队列 | 框架字节上限不能替代现有 repeated 解码前数量上限 |

gRPC 的 HTTP/2 帧与消息前缀不同于当前六字节前缀, 属于线协议替换.
过去的 MessageID 清单作为旧版本记录保存, 不伪装成仍兼容的线上分派机制.
[官方线协议](https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md).

## 3. 基础 RPC 形态, 待原型确认

- Supervisor 准入: 本轮沿用已有实现, 不为 Star/Planet 性能实验改写成 Go gRPC.
  后续正式迁移若涉及该入口, 仍须保留首次 CAS 基线和 Planet 刷新不递增准入代次的规则.
- Star/Star: 每个方向建立长期复制 RPC. 应用中的入站/出站表示复制会话角色,
  不把 Channel 直接等同于唯一物理 TCP. 本轮不顺带改变双向互联的拓扑策略.
- Planet/Star: Planet 发起唯一活动双向会话, Star 可以在响应流主动发送消息.
  候选切换前终止旧会话, 已建立会话不因更优候选出现而自动迁移.
- SDK 接口不在本轮原型或测试范围内, 不生成和运行 SDK 测试客户端.

流中两端读写需要独立推进, 正常关闭须回收自己的 stream、task 和 channel.
不要在应用自己的候选退避外再叠加不可观察的无限 RPC 重试.
已建立的流断开后由 Astra 重新建立会话并携带恢复信息; 框架重连不代表同步已恢复.
[官方流控](https://grpc.io/docs/guides/flow-control/), [重试](https://grpc.io/docs/guides/retry/).

当前 TLS exporter 在 `common/src/identity.rs` 直接从 rustls 连接取得.
原型须验证客户端/服务端都能把认证连接上下文交给 RPC 会话, 并维持同等重放防护.
此项未验证前不能宣称迁移只需要更换读写 API. Supervisor 的证书角色和地址 SAN 校验继续保留.

## 4. 对比矩阵

当前骨架只有认证和控制消息, 业务广播尚未实现. 因此需要相同的合成业务消息负载用于两种传输,
单独报告传输微基准、认证控制流程和故障回归, 不拿 Ping 循环推断整个系统性能.

主负载现已扩展为共享发布源、真实字符串键 HashMap、连续版本广播和最终状态摘要核对.
Registry 分别保留 100/1000/10000/100000 项独立 128 B 数据, Catalog 保留 1000 项.
每个源更新生成一次新内容, 分发时共享不可变 Bytes. 混合负载为 25% Registry + 75% Catalog,
穿插少量 16 KiB 快照片段. 正常 2000 次源更新/s, 突发 8000/s; 每个接收端仅有
20 次诊断控制探测/s 和 5 次小发布/s, 数据更新没有逐条 ACK. 另测一个接收端暂停 200 ms,
上行控制任务继续运行. 专项 Catalog 负载不穿插快照片段, 测 64/256/1024 B,
以 2000/8000/20000/60000 次源更新/s 逐级加压, 每次更新广播给 4 个接收端.
每 128 次应用后回报累计水位, 发布端以自身单调时钟测计划发布到应用确认的抽样延迟.
计划时间避免漏掉发压器落后, 反向确认使该值包含返程, 不宣称单向延迟.
缓存初值在测量前预置, 不冒充全量同步. 发布调度、队列和缓存逻辑由两种传输共用.
该模型验证消息调度, 不冒充完整业务存储/快照恢复或已实现的 Star 网格.

| 维度 | 计划测量 |
| --- | --- |
| 消息大小 | 256 B, 1 KiB, 16 KiB; 区分有效载荷和实际线上字节 |
| 发送模式 | 单条与等量批次, 两端使用相同刷新/批次策略 |
| 流向 | 单向推送、双向流、单次请求响应 |
| 扇出 | 从 1、4、16 逐步扩大至 64 个接收会话; 受实际内存和运行条件约束 |
| 持续负载 | 相同固定提供速率下的 P50/P95/P99, 另测饱和吞吐; 记录超时/失败及未完成请求 |
| 资源 | 每进程 CPU 时间、RSS、可用内存, 每消息分配次数/字节, 总有效消息数/字节 |
| 连接成本 | 单独测冷启动 mTLS/准入与热连接稳态, 不把二者混成一个延迟数字 |
| 异常 | 慢消费者、无读取、断线、取消、Supervisor 离线、候选切换、半关闭及资源回收 |
| 平台与角色 | Rust Star/Star, Planet/Star; Windows/Linux 本机和跨机实测 |

测量规则:

1. 同样的 release 优化、工作线程、TLS 1.3/证书验证、帧或消息限额、队列字节预算和压缩策略.
2. gRPC 复用 channel 和长期流; TCP 同样复用连接. 不用逐消息建 RPC/连接的低效实现制造差距.
3. 两者同样逐消息编码广播数据. TCP 推流合并至多 16 个已就绪完整帧后 write_all + flush,
   不等待凑满批次; gRPC 允许框架合并 HTTP/2 输出. 控制帧单独立即刷新.
   实测比较这两个具体实现, 不能将差异全部归因于协议本身或视为优化 TCP 的理论极限.
4. 预热后至少五轮交错运行; A/B 不同时争用 CPU 或链路, 原始样本和失败全部保留.
5. 固定提供负载与饱和测试分别报告. 使用同一进程单调时钟测 RTT/确认延迟,
   不通过未校时的两台机器相减估算单向延迟; 慢响应不能抑制后续发送并隐藏排队延迟.
6. Ubuntu 单任务编译, 逐级扩大运行规模, 持续检查内存; 触及预算则停止该规模并标为未完成.
   VM 启用动态内存, 不把启动内存当成硬上限. 按当前可用内存设置 256 MiB 停止保护,
   记录 VM 实际内存/CPU/网络和其他负载; 配置漂移或系统交换影响结果时重新采样.
7. 先做消息流原型及对比, 再通过同等认证和 Star/Planet 故障回归. 不添加 SDK 测试;
   生成接口能工作不能代替安全与资源边界验证.

Tonic 有自己的 RPC 缓冲, 需要计入实际内存预算, 不能仅据 Bytes 类型承诺端到端零拷贝.
[Tonic 缓冲文档](https://docs.rs/tonic/latest/tonic/codec/struct.BufferSettings.html).

## 5. 软件缺口与项目内位置

维护者已明确允许以下依赖, 两端项目缓存均已补齐. 现有 Tokio、rustls/ring、Prost、
protoc 36.1 和 Rust 工具链复用, 未安装全局软件或改变系统配置.

| 软件 | 用途 | 来源 | 两端各自项目内位置 |
| --- | --- | --- | --- |
| tonic, tonic-prost, tonic-prost-build 0.14.6, 及必要传递依赖 | Rust gRPC 客户端/服务端和显式代码生成 | crates.io / grpc-rust | `build/deps/cargo` |

Tonic 原型只开启需要的 transport/codegen 和选定 TLS 接入路径, 复用现有密码提供者,
不引入系统信任根或无关压缩/云服务集成. 本轮不下载 Go gRPC 或 Go RPC 生成器.
依赖解析若要求升级项目现有精确锁定包, 先报告具体差异, 不擅自升级.
新增 C++、C#、Go 或 Python gRPC 运行库不在本轮范围内.

版本依据: [Tonic](https://docs.rs/tonic/0.14.6/tonic/),
[Prost codec](https://docs.rs/tonic-prost/0.14.6/tonic_prost/),
[代码生成](https://docs.rs/tonic-prost-build/0.14.6/tonic_prost_build/).

## 6. 后续产物与退出条件

已产出独立对照程序、锁文件、显式生成的 RPC 源码、可复现命令、660 次原始试验和最终清理记录.
两端正式 Rust 工作区各通过 39 项测试, 原型各通过 14 项测试及 Clippy; 无 SDK 测试或 Go gRPC 下载.
正式 v3 采用缓存预置后两秒固定负载、五轮交错运行; 没有额外稳定负载预热,
没有完成上文规划中的饱和极限、长时恢复和完整 Supervisor 故障迁移评估. 这些边界不写作已通过.

当前不执行正式迁移. 如继续评估, 应先补齐跨机错误采集和根因定位, 再依据实际业务的延迟/CPU 预算
开展更长的稳定负载和恢复验证. gRPC 能生成接口并不等于无性能损失, 也不会自动实现业务同步恢复.
