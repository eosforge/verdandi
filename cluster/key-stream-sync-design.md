# 按 Key 对账与流式同步设计

日期：2026-09-12。状态：设计方向已确认，协议细节待细化，尚未实现。

本文记录未来 Star 后端的 Subscriber / Selector 同步方案：每个 Key 独立维护版本和有界更新历史，
SDK 在连接或切换入口时按订阅范围对账，随后通过同一条 gRPC 流持续接收更新。

适用角色与转发方向沿用[星图架构](../galaxy-architecture.md)。当前 C++26 服务仍是
[连接骨架](../cluster-cpp/README.md)，本文不修改现有 Redis SDK、C ABI、Protobuf 或持久化格式。

## 1. 本轮确认的方向

1. Subscriber / Selector 建立流后先鉴权，确定可访问的订阅范围，再进行初始同步。
2. 同步以 Key 为单位：各 Key 有独立版本和近期历史，SDK 无须按接入 Star 或发布来源维护日志游标。
3. 每个 Key 的版本由其合法发布者维护。发布者重定向到其他 Star 时保留版本进度，接入节点不重新编号。
4. SDK 连接时对账整个订阅范围。所需历史完整就增量补齐，历史不足就恢复该 Key 的最新完整状态。
5. 对账完成后继续使用同一条 gRPC 流推送新增、修改、删除及必要的领域元数据变化。
6. 对账负责恢复错过的删除；“已删除”和“当前副本未知”必须区分。
7. SDK 切换 Star 后仍能使用每 Key 的已有版本，不因入口变化而默认恢复整个范围的大型快照。

下文的正确性约束是落实这些方向所需的边界；具体编码、数值上限、写者恢复、回收算法与确认门槛见第 11 节。
不以这份设计记录声称网络业务同步、跨 Key 事务或持久确认已经完成。

## 2. Key、版本与角色责任

Key 是带业务命名空间的完整身份，至少需要区分 Galaxy、业务领域及所属范围。
Catalog 路径与 Registration 身份沿用各自领域规则，具体组合编码尚未冻结。
Key 不包含当前接入 Star、连接编号或当前传输路径；这些变化不应制造新的业务数据身份。

| 角色           | 责任                                                                           |
| -------------- | ------------------------------------------------------------------------------ |
| 发布者         | 为自己有权写入的 Key 维护版本、构造更新、处理重试和重定向                      |
| Star           | 校验写入权限与版本，接纳状态，维护历史，复制并向获授权客户端提供对账与推送     |
| Planet / Relay | 转发写请求，缓存获授权状态，使用共同同步规则向下游提供数据；不自行取得写者权威 |
| Subscriber     | 按 Key 维护 Catalog 本地视图，通过对账和增量恢复；业务读取使用本地视图         |
| Selector       | 维护有效 Registration 集合，在本地执行选择；网络同步与具体选择策略分开         |

每个 Key 在同一写者代次内只有一个合法发布者。多个发布者写不同 Key 时不需要统一版本序列。
同一个 Key 的写者替换需要授权与旧写者隔离，不能通过更换 Star 或提交更大的整数自行取得权限。

本文 version 表示未来按 Key 同步所需比较的业务状态版本，不直接替换现有 SDK 中所有名为 Version / revision 的字段。
Registration 的内容版本、租约、绑定代次和进程 UUID 保持不同含义，见第 7 节。

## 3. 发布者版本规则

发布者在同一 Key 的有效写者代次内维护严格递增的版本。其他 Key 的版本大小不参与比较。
发布者通过 Star A 发布到版本 101，重定向 Star B 后继续产生更高版本；Star B 不重置它。

```text
发布者 -> Star A：Key X，版本 100
发布者 -> Star A：Key X，版本 101
入口切换
发布者 -> Star B：Key X，版本 102
```

必须保持以下不变量：

- 新业务状态采用更高版本；发布者主动删除也属于该 Key 的版本序列。
- 同一次操作重试保持原版本与原内容。同版本、同操作和同内容是重复请求；同版本不同内容是冲突。
- 回复丢失属于结果不确定，重定向后先重试原操作或对账，不能单凭断线就认定原操作未生效。
- 副本保留已接纳状态的版本和身份；旧更新不能覆盖新更新或更新的删除状态。
- 发布者不能在重启后复用已使用的版本。持久保存进度、恢复确认和写者代次的具体方案仍待确定。
- 从一个可能落后的 Star 读取“当前最大值加一”不足以证明恢复安全。

版本的位宽、溢出、是否允许跳号以及写者代次编码尚未冻结。同步不能仅凭版本号处于最大最小值之间就认定历史完整。
首次重放及每个 Patch 都必须有可验证的基线，不能把“高版本存在”当作“中间更新全部可用”。

## 4. 服务器的数据组织

逻辑上每个 Key 有自己的 Stream，物理上可以共用日志段、缓冲区和索引。
不要求为每个 Key 创建独立线程、gRPC 连接、文件或数据库实例。

| 结构                  | 保存内容                                                          | 用途                       |
| --------------------- | ----------------------------------------------------------------- | -------------------------- |
| 当前状态表            | Key、合法写者信息、版本、存在或删除状态、完整正文及必要领域元数据 | 读取、比较和完整状态恢复   |
| 按 Key 索引的有界历史 | 近期已接纳更新及其可重放基线、目标版本                            | 增量追赶与实时推送         |
| 订阅范围索引          | 当前授权范围内需要枚举的 Key，以及删除或覆盖依据                  | 发现新 Key，恢复错过的删除 |
| 会话同步状态          | 订阅范围、会话代次、对账进度、同步期间变化和有界发送资源          | 对账与实时推送之间的交接   |

示意如下，数字只是一个写者代次内的示例：

```text
Key A：当前版本 12，存在，保留历史 9…12
Key B：当前版本 38，存在，保留历史 35…38
Key C：当前版本 7，已删除，保留必要的删除依据
```

状态安装、历史可见性和订阅通知必须通过同一个受控提交过程衔接，失败不能留下部分发布的状态。
历史引用对应版本的不可变内容，不能引用会继续改变的“当前值”对象。
不同 Star 可以保留不同长度的历史，但同一 Key、同一合法版本必须具有相同的业务含义。

历史用于恢复当前视图，允许历史缺失后跳到该 Key 的完整状态；它不是保证永久重放每次业务事件的审计日志。
内存接纳、复制完成、落盘及业务成功的区别沿用待细化的存储确认契约，不由“写入了 Stream”自动决定。

## 5. 对账与持续推送

### 5.1 会话生命周期

```text
建立 gRPC 流
    -> 鉴权并确定订阅范围
    -> 登记更新订阅，开始记录同步期间变化
    -> 分批对账 Key 与版本
    -> 补齐单 Key 历史或完整状态，并处理删除
    -> 接续同步期间变化
    -> SyncComplete
    -> 持续推送
    -> 断开后重新鉴权、对账
```

一个 SDK 同步会话使用一条有序流承载多个 Key 的消息。初始清单与数据分批传送，不为每个 Key 发起独立 RPC。
SDK 提交已有 Key、版本和必要状态；服务器枚举整个授权范围，同时检查 SDK 提交但本端暂未找到的 Key。
首次连接没有本地数据，因此需要获取该范围的完整基线。

### 5.2 每 Key 的对账结果

| 对账情况                           | 处理方式                                                   |
| ---------------------------------- | ---------------------------------------------------------- |
| 同一合法版本、状态及相关元数据一致 | 跳过正文                                                   |
| SDK 落后，所需历史可完整重放       | 按该 Key 的顺序补齐历史                                    |
| SDK 落后，历史不完整               | 发送该 Key 最新完整状态及对应版本                          |
| SDK 没有服务器已知的新 Key         | 发送当前完整状态或必要的删除信息                           |
| 服务器掌握更新的删除版本           | 返回明确删除结果，SDK 移除旧值并保留必要版本依据           |
| SDK 版本更高                       | 保持已知新状态，服务器修复或报告同步未完成，不用旧状态覆盖 |
| 同一版本不同受版本约束的内容       | 报告冲突，不能按接收顺序覆盖                               |
| 本端没有该 Key，也没有删除依据     | 返回未知或待修复，不能直接推断删除                         |

表中一致性比较覆盖受版本约束的状态。租约等独立变化不能只凭内容版本相同而被跳过。
客户端提供的版本只用于表达其已有进度，不自动构成服务端可接纳状态或写入权限的证明。

### 5.3 从对账交接到推送

必须在开始枚举前建立变化捕获，覆盖同步期间新增、修改、删除、订阅成员变化和必要的租约更新。
分页枚举需要完整性规则，不能因中途新增或删除 Key 就漏项、重复覆盖新状态或误判删除。

恢复 Key A 的完整值时，固定 A 在版本 12 的内容；发送期间产生的 13、14 通过后续更新接续。
这只要求固定该次读取的单 Key 状态，不要求同时固定整个 Galaxy 在一个全局日志位置上的快照。

SyncComplete 是当前会话、当前范围完成对账并建立无缺口增量交接的标记。
它不是全群所有副本已经相同、后续不再产生更新或全部内容已经持久化的证明。
SDK 在完成前处于 Synchronizing，完成后发布可用视图并进入 Live；未知或未修复的缺口不能被忽略后标为完成。

gRPC 保证同次 RPC 每个发送方向的消息顺序；服务端发送调度和 SDK 状态应用也必须保持所需顺序。
单条流的传输顺序不构成跨 Key 的全局提交顺序。此方案不承诺所有 Key 来自同一时刻，也不提供跨 Key 原子事务。
断开、重连或订阅范围变化使用新的会话代次，旧回调不得修改新会话视图。

## 6. 删除与完整性

删除既是需要推送的变更，也是当前状态的一种版本化结果。
SDK 错过删除事件后，通过对账仍应获知该结果，不依赖无限保留删除事件历史。

```text
SDK：Key X，版本 100，存在
服务器：Key X，版本 101，已删除
对账：返回 X 的删除版本 101
SDK：移除旧值，拒绝随后迟到的版本 100
```

“没有该 Key”与“已确认该 Key 删除”不同。切换到落后 Star 时，本端缺失可能来自尚未复制、权限范围变化或确实删除。
权限变化可以使数据退出本地授权视图，但不等于发布者删除了业务数据，协议必须区分。

完整清单缺项只有在范围、枚举完成、版本覆盖和删除依据都足以证明时，才可以作为移除本地值的依据。
不能因为分页中暂未出现，或某个落后副本查不到，就执行无条件清理；具体证明形式仍待设计。

完整状态恢复应在已验证范围内处理本地多余项，不能只覆盖出现的 Key 而永久保留已经删除的旧值。
移除本地正文不意味着立即忘记删除版本，切换入口后同样要防止旧值重新进入视图。

历史裁剪与删除依据回收是不同操作。删除日志裁剪后仍需保留删除状态、版本下界或其他可验证的旧状态拒绝依据。
回收必须考虑离线副本、旧发布者、SDK 缓存与新成员恢复；仅经过一段时间或日志已满不能证明安全。
超过有效恢复范围的参与者需要受控重建，不能携带旧值重新参与合并。具体回收方案属于实施前待决项。

## 7. 重定向、换绑与租约

Publisher 从 Star A 重定向到 Star B，或经 Planet 切换上游时，Key 与已产生的内容版本保持不变。
Subscriber / Selector 携带各 Key 已应用版本重新对账，不依赖 A 的本地日志位置或发布源游标表。
目标节点具备所需历史就补齐；只有相关 Key 的历史不足时才恢复其完整状态。

Planet 全量缓存授权状态，不代表所有缓存 Key 都由它管理或有权重新发布。
换绑时恢复的登记关系仅限仍有效、获授权的下游关系，不能把全量副本变成自身发布源。

Registration 保持以下边界：

- 服务进程仍在运行时，入口换绑不改变 Registration 身份；进程重启继续遵守新 UUID 规则。
- 内容版本由其发布者维护；续租、租约期限和接入代次不能误用内容版本或 Star 进程 UUID 表达。
- 旧绑定的撤销、旧连接回调及旧租约到期动作，不能删除新绑定下已经恢复的有效登记。
- 服务端判定租约到期应携带相应租约与绑定依据，不能冒充发布者自行分配新的内容版本。
- 租约有效性不能因缓存读取、快照重放或连接仍在线而延长；Selector 使用缓存仍须遵守有效性规则。

租约、主动撤销、重新登记与同步版本如何组合仍需领域协议细化。
同步设计不改变 Star / Planet 存储模式、Supervisor 离线授权或持久确认的既有边界。

## 8. 容量与性能方向

按 Key 恢复减少了一个 Key 历史缺失导致整个范围重新传正文的情况，但首次连接仍有 O(Key 数量) 的枚举与状态传输成本。
一个特别大的 Key 仍需分块恢复；批量对账也会消耗 CPU、内存与带宽，不能承诺无卡顿。

实现建议：

- 当前正文尽量采用不可变拥有型存储；历史和发送任务可共享对应版本，避免每个下游深拷贝。
- 清单、正文、历史及解码按批次执行，设置单批条数、字节数和处理预算。
- 同时限制单 Key 历史和全服务历史总字节，避免 Key 数量增长绕过容量约束。
- 同步期间变化、在途发送、旧版本引用、临时视图、并发恢复及旧视图回收都计入预算。
- 不在长锁或 gRPC 回调中完成大规模复制、序列化和索引重建；共享引用的全表扫描同样是 O(N)。
- 客户端落后或超预算时明确报告恢复失败或重新对账；不能无限阻止裁剪或丢数据后仍报告 Live。
- 控制恢复并发，为其他客户端的正常更新保留资源。长期消费慢于产生速度时，反复恢复不能保证追上。

gRPC 流控只覆盖其传输推进，应用创建的消息、历史和临时视图仍需自己约束。
数值默认值、物理容器、共享存储方式和是否缓存完整值编码，均以实测决定。

## 9. 与既有设计的关系

本文作为未来 Star 后端按 Key 同步方向的最新记录，细化[Star 设计](design.md)的 SDK 同步部分。
旧 [Core 草案](core-design.md)中的来源 Star 分区可作为内部复制机制另行审核，不直接成为 SDK 恢复游标。

此前讨论的“各 Star 按接收顺序编号，SDK 换 Star 后默认全量恢复”不作为当前同步目标。
SDK 也不需要维护发布来源数量规模的游标向量；恢复基线来自本地已有的各 Key 版本与必要领域状态。
本轮不要求共享全局版本或统一排序整个 Galaxy，Star 间复制与冲突校验仍须独立设计。

现有 Redis 协议及 SDK 的实际行为继续由原文档与测试定义。
本轮只记录未来后端的设计，不新增运行时存储引擎、依赖、业务消息编号或 SDK 公共 API。

## 10. 实施时需要覆盖的验证

以下是验收场景，尚未执行为本设计的测试结果：

1. 首次无缓存连接，完整枚举授权范围并进入 Live；未鉴权时没有业务数据。
2. 各 Key 版本相同跳过正文；历史完整时重放，不完整时仅恢复相关 Key。
3. 更新基线缺失、重复、乱序、同版本冲突和版本边界均不产生静默覆盖。
4. 枚举期间新增、删除、修改，以及单 Key 完整状态传输期间的更新均不遗漏。
5. SDK 错过删除事件且历史被裁剪后，对账仍移除旧值；迟到旧更新不能复活数据。
6. 切换到落后 Star 时保留已知版本；未知 Key 不冒充已删除；补齐前不报告同步完成。
7. 发布回复丢失、重定向后重试保持幂等；未授权客户端不能通过自报高版本接管 Key。
8. 发布者重启、写者替换、Key 删除后重建及旧副本回归遵守代次和回收规则。
9. Registry 旧租约到期、旧撤销和旧会话回调不能影响新绑定。
10. 新订阅范围与授权变化、分页不完整、取消、慢消费者和容量拒绝不泄漏数据或资源。
11. 大 Key、大 Key 数量和并发恢复时记录 CPU、峰值内存、正常读写延迟及恢复耗时。
