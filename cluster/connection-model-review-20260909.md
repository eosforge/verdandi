# Peer 单连接与双连接审核

日期: 2026-09-09. 状态: 设计比较, 推荐单条全双工 TCP, 并由后注册者固定连接先注册者; 待用户选择. 现有 CORE-002 双连接决定和代码尚未改变.

后续 CORE-012 已规定 Peer ID 为进程级 UUID. 本文跨重启复用身份和登记序号的原假设已替换: 同一进程重试可复用序号, 新进程按新 UUID 重新登记; Supervisor 离线时的新进程登记仍需单独设计. 连接数量本身仍未改选.

## 1. 结论与前提

在 [Supervisor 加入方案](supervisor-design.md) 下, 推荐每对 Peer 保留一条全双工 TCP, 在连接内部独立管理本端发布与远端接收. 新节点取全名单后主动连接旧节点, 旧节点记录它后即可利用该连接双向同步, 不必再拨一条镜像连接.

这项推荐来自连接生命周期和资源成本的比较, 不是吞吐基准结论. 当前只有网络控制底座, 尚未实现 StateStore、OwnerPush 或 ReplicaRepair, 所以现在评估调整的业务迁移成本较低.

TCP 本身是全双工, 两端具有发送与接收状态, 不是一端发送时另一端必须等待. [RFC 9293](https://datatracker.ietf.org/doc/html/rfc9293) 定义了这些传输语义. 当前镜像方案用两条全双工 TCP 各承载一个主要正文方向, 并没有在同一个正文方向上使用两个并行数据通道.

## 2. 结构与计数

```text
单连接:
    A ===== 一条 TCP ===== B
       A-owned State --->
       <--- B-owned State

双连接, 当前设计:
    A.client ---- TCP 1 ---- B.acceptor    B-owned State: B -> A
    B.client ---- TCP 2 ---- A.acceptor    A-owned State: A -> B
```

| Peer 数 | 单连接总数 N*(N-1)/2 | 双连接总数 N*(N-1) | 每节点 socket: 单 / 双 |
| --- | ---: | ---: | ---: |
| 3 | 3 | 6 | 2 / 4 |
| 16 | 120 | 240 | 15 / 30 |
| 64 | 2,016 | 4,032 | 63 / 126 |

只统计稳定 Peer 数据连接, 不含 Supervisor、SDK、握手中的候选或重连残留. 这些是公式计数, 不是容量验证. 两种方案仍是 O(N²) full mesh, 单连接只减少常数, 不解决任意规模扩展.

## 3. 优缺点

| 维度 | 单连接 | 两条镜像连接 |
| --- | --- | --- |
| 正常加入 | 新节点拨通即具备双向通道 | 新节点连接后还需旧节点反向拨号 |
| 固定资源 | socket、Hello、保活和连接取消对象较少 | 数量较多, 但业务负载内存不必按同样比例增长 |
| 数据职责 | 每端同时负责本端发布、远端接收; 两个逻辑模块可分开 | acceptor 发布、client 接收与 socket 角色直接对应 |
| 重连 | 一次连接恢复后重新同步两个方向 | 两个方向独立退避和恢复, 需要处理只恢复一条的状态 |
| 重复连接 | 同时拨号需要双方一致的连接选择规则 | 可以各保留一个方向, 跨方向冲突较少; 同方向重复和旧实例仍要处理 |
| 故障范围 | 一次会话重置会中断双方同步 | 单个 socket 故障可能只影响一个复制方向 |
| 背压 | TCP 两向各自有流控, 同向控制帧与正文需要调度 | 两个复制会话更易分别限流, 部分控制请求与另一个 owner 的正文分开 |
| 可观测性 | 每 pair 一条物理边, 仍需分别展示 Tx/Rx 同步状态 | 每 pair 两条物理边与独立错误, 多出 1/2 就绪情况 |
| 当前改动 | 需改会话去重、反向拨号及未来业务方向规则 | 与现有网络代码最接近 |

固定连接成本减少不等于总内存减少一半. 本端发送和远端接收所需的正文、dirty、快照与业务队列依然存在. TLS 启用后单连接通常需要更少的握手/会话上下文, 但节省多少需实测.

双连接也不是两条独立容灾路径: 两个 socket 通常仍依赖相同 Peer 进程、机器和网络. 按当前正文方向约束, 剩下一条也不能自动承担两个方向的全部同步, 除非再增加切换协议. 当前 Core 对任一方向缺失会 Degraded, 其业务收益还受这个就绪策略限制.

## 4. 性能与背压的准确边界

单连接的 A -> B 与 B -> A 是不同字节流方向, 不能把它们描述成互相串行抢用一个发送窗口. 但 A 发给 B 的 A-owned 正文与针对 B-owned 数据的应用层确认/请求, 在单连接中共享 A -> B 的字节流. 这里存在应用层排队与请求依赖, 需要合理调度.

双连接可让针对某个 owner 的一部分反向控制请求避开本端 owner 的正文队列, 这是实质优点. 但它不是专用控制连接: 每条连接自身的正文、Pong 和其他控制响应仍可能共用写方向, 也仍然存在有序传输和大帧阻塞.

两种方案都应做到:

- 唯一 writer 串行写完整帧, 不让多个任务交错写帧头与正文.
- reader 与 writer 可并发推进; 不要两端同时等待大正文写完后才继续读.
- 控制帧在帧边界优先, 并设公平预算; 已进入 TCP 的正文不能被后来的高优先级帧插队.
- 大量小值的全量同步仍可能形成长队列, 按总字节限制在途量, 大正文按需要有界分块.
- 控制与数据都有容量边界, 慢接收方不能导致 OOM 或让读任务永久卡在业务队列上.

Tokio 的 [TcpStream::split / into_split](https://docs.rs/tokio/1.53.1/tokio/net/struct.TcpStream.html#method.split) 支持同一 socket 的并发读写. 借用 split 不要求额外 socket, owned split 可以独立放进任务但有一次堆分配成本. 单连接不意味着必须合并成一个巨大的串行状态机.

当前 [connection.rs](src/connection.rs) 的 keepalive loop 处理的是有界控制消息, 部分分支会等待一次完整写入. 它不能作为未来双向大数据写入不会阻塞读取的证据. 加入业务复制时应重新审查收发调度; 本次不把尚未实现的大正文路径登记为已复现 BUG.

引用式广播、共享不可变 Bytes、Protobuf 编码次数与 socket 数是不同问题. 两种方案都可让一个 StateVersion 编码一次再向不同远端共享缓冲区; 单连接不天然少一次正文拷贝, 双连接也不天然吞吐翻倍.

## 5. 单连接需要补上的设计

### 5.1 建立方向只保留为传输信息

每端都只主动发布 self-owned State, 接收远端 owner 状态; 这个数据所有权规则仍保持. 需要修改的是“只有 TCP acceptor 可以发送普通正文”, 因为单连接发起方也要发布自己的状态.

可按 `PeerLink { transport, outgoing_replication, incoming_replication }` 划分内部职责. framing 仍是 MessageID + PayloadLength + payload. 请求关联需限定在当前会话和请求发起方的上下文, 两端可以各有自己的编号, 不必为此引入通用多路复用协议.

### 5.2 同时连接与重连

首次加入确实依赖新 Peer 主动联系完整名单中的所有旧 Peer. 这是“不由 Supervisor 推送新成员、Peer 不转发节点介绍”的结果, 当前双连接方案也有相同依赖: 旧 Peer 在收到新节点的 Hello 之前不知道它, 因而不能先发起反向连接.

例如 N 已连接 A, 但还未连接 B, 则 B 尚不知道 N. 单连接下 N 必须继续重试 B; 双连接下也必须先完成 N -> B 的接触, B 才能安排 B -> N. 对尚未获知新节点的旧成员, 双连接本身不能补救单向不可达或新节点停止重试. 新节点必须保留完整目标表, 不能把连接上部分成员等同于全部加入完成.

首次握手后双方已记住彼此, 从能力上双方都可以尝试重连. 但为减少竞争和状态分支, 后续审核推荐按 5.3 固定后注册者重连; 下面的双边竞争处理仅用于比较另一种方案, 不应同时作为固定方向方案的必需机制. 已建立的 TCP 上, 双方都可以主动发起业务同步和发布, 不需要由新节点代理所有请求.

新加入时必须允许新节点主动拨号, 不宜一开始就规定“只有 ID 较小者可以拨号”: 如果新节点 ID 较大且旧节点还不知道它, 两边会一直等待.

当两端都知道彼此并同时重连时, 可能暂时产生两条候选 socket. 不能各自保留最先到达的一条, 否则双方可能关闭对方保留的连接. 需要在握手阶段使用双方一致的规则选择同一条, 例如发生竞争时按稳定 Peer ID 确定优先发起方向. [Erlang distribution handshake](https://www.erlang.org/doc/apps/erts/erl_dist_protocol.html) 就显式处理 simultaneous connect 并按节点名排序仲裁.

稳定连接、在途候选和新 boot 替换必须分别处理; 不应为了调整拨号方向持续重建健康连接. 具体握手确认与旧 generation 退出规则尚未设计完, 这里没有把一个简单 ID 判断当成完整正确性证明.

### 5.3 固定后注册者连接先注册者, 推荐待选择

这个方向适合 Supervisor 登记与完整名单模型. “新旧”建议定义为首次成功登记的稳定顺序, 不使用进程启动时间、本机时钟或当前 TCP 建立时间.

若选择此方案, Supervisor 为新进程 UUID 分配唯一递增的 `join_order: uint64`, 与身份和地址一起保存. 同一进程的注册重试返回原序号; 进程重启使用新 UUID, 重新登记并取得新顺序, 不恢复旧进程序号. 完整名单携带各成员的序号; 首版单实例 Supervisor 已需串行登记, 因而不引入选举或分布式时钟. 此序号只决定谁拨号, 不是需要各 Peer 对账的拓扑 revision. 旧进程记录的安全替换和回收须随 CORE-012 审核.

```text
规则: self.join_order > remote.join_order 时, 本端负责连接与重连.

A = 1, B = 2, C = 3:
    B -> A
    C -> A
    C -> B
箭头只表示拨号方向, 每条 TCP 上的数据始终可双向传输.
```

- 新节点取全名单后, 只为序号小于自己的成员创建拨号任务. 正常首次注册时, 其他成员都比它早.
- 序号较小的一端接收入站、登记对端并用同一 socket 双向同步, 不创建反向拨号任务.
- 连接断开后仍由原先序号较大的一端退避重连. 接收方继续监听, 不因等待时间较长而自动翻转方向.
- 注册响应丢失后重试可能拿到包含更晚节点的新名单; 仍按原序号筛选目标, 不能因为出现在本次名单中就全部主动拨号.
- 两个并发新节点由 Supervisor 分配不同顺序, 后登记的一方知道并连接先登记的一方. 不要求进程顺序启动.
- 双方按可信配置及最终身份规则核对对端序号和方向. 不能把普通 Hello 自报序号当成额外的身份授权证明; 生产身份安全仍另行定义.

每个无序节点对只有一个指定发起方, 可消除正常的双边同时拨号竞争. 同一发起方的重复重试、旧 socket 残留、新 boot 与迟到关闭仍可能出现, 所以每目标至多一个在途拨号、会话 generation、重复会话处理与超时不能删除.

代价是指定方向必须可达: 若只允许旧节点主动访问新节点而反方向被阻断, 本方案不会自动反向补救. 固定方向的代价需由部署连通性约束接受, 不应悄悄增加双边兜底从而重新引入仲裁.

Supervisor 离线时, 已运行的进程用当前 UUID、序号及名单继续运行. 新进程没有该 UUID 对应的登记顺序, 不能复用旧 UUID 或借用旧序号参与拨号排序. 若要求 Supervisor 离线期间也允许整个群组重新启动, 这套登记顺序方案需补充设计并重新验证, 不能宣称仅持久化旧名单就已满足. 成员替换、回收和重新入群仍是待审部分.

## 6. 建议与后续验证

推荐单连接并固定后注册者拨号的原因是: 新节点加入与重连职责一致, 正常路径不需要双边连接仲裁, socket 生命周期更少, 数据职责可用两个逻辑模块表达. 当前业务复制尚未实现, 适合在其落地前决定. 与先前允许双方重连的候选相比, 这需要保留一个稳定注册顺序, 换来更少的连接竞争分支.

保留双连接的主要理由应是明确需要两个复制方向独立恢复, 或测出同向控制流与正文竞争显著影响尾延迟. 不宜仅因为双连接“看起来更并行”就为全部节点增加 socket.

若选择固定方向单连接, 先验证正常/并发注册、重复请求保留序号、重试快照含更晚成员、任一端重启、Supervisor 离线、错误方向拒绝、同向重连残留、旧 boot 迟到及完整关闭. 反方向单独可达时应明确报告不可连, 不偷偷切换策略. 再使用相同数据与预算比较双向小值更新、批量初始同步、慢接收、限带宽和中途断线, 记录吞吐、P99 延迟、RSS、CPU、在途字节及恢复时间. 当前没有这些对照测试结果.

本次仅做方案审核与文档记录, 不改变已接受的双连接目标或 Rust/Proto 实现, 不下载依赖.
