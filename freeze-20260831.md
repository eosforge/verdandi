# Verdandi Alpha Source Freeze — 2026-08-31

Scope update, 2026-09-02: the Leader requirement recorded in this historical
freeze was withdrawn from every release target. Redis Sentinel failover remains
backend recovery; it does not add an application Leader API.

## 1. Freeze meaning

The Git commit containing this document is the first reviewable Verdandi Alpha
source freeze. It freezes source, generated Lua, shared conformance vectors,
tests, documentation, dependency locks, and the bounded regression evidence
listed below. It is the runtime source basis for the later `0.1.0` Alpha release
decision, but it is not a stable wire-compatibility or production-readiness
declaration. At this historical checkpoint, Leader, desired-state, and
acknowledgement modules remained outside the implemented freeze. The later
2026-09-02 scope decision removes Leader from that list.

The post-commit twelve-hour endurance campaign must run from a detached
worktree at this exact commit. It must not read mutable source from the review
working tree. Registration/Selector and Catalog use separate Redis ports,
containers, logs, and result files so that the maintainer can continue code
review while both workloads run.

## 2. Final review changes

- Added direct Go tests for every `internal/validate` boundary: omitted/default
  values, closed ranges, explicit zero, exact milliseconds, ASCII-only Zone
  grammar, and the 1/32/33-byte name boundaries. The package now has 100%
  statement coverage.
- Made every project-owned C, C++11/14/17, and C++23 target compile with strict
  warnings as errors. GCC/Clang use `-Wall -Wextra -Wpedantic -Wconversion
  -Wsign-conversion -Werror`; MSVC configuration uses `/W4 /WX`, with modern
  conformance switches for C++ targets.
- Added C++ consumption of the shared strict-JSON configuration corpus. This
  found and corrected one cross-language diagnostic drift: duplicate or
  unknown JSON members now report the stable field `json` in Go, Rust, C++,
  and therefore C#; value, type, relationship, and range errors retain their
  exact configuration field.
- Removed an unused compile-time local in the C++23 single-field Schema path by
  expanding the tuple size directly into `std::make_index_sequence`. This is a
  compile-time cleanup and adds no runtime branch or allocation.
- Made the Rust deadline heap use `Ordering` for its three-way update decision.
  The change preserves runtime behavior while allowing both current stable Rust
  and the declared Rust 1.85 minimum toolchain to pass strict Clippy.
- Added C# concurrent root disposal and finalizer-pressure regressions. Eight
  workers may race root `Dispose` while borrowed operations are active; repeated
  disposal remains idempotent. Abandoned published Registrations are finalized,
  their native handles are released, and their membership fields disappear.
- Redacted a destroyed historical test credential, ignored local IDE and
  coverage artifacts, and retained the public self-signed TLS fixture only as
  explicit test data. No generated output was edited by hand.

No speculative hot-path rewrite was accepted without comparative evidence.
The specialized Lua programs, Registration mailbox, one-writer lifecycle,
Selector immutable view, Catalog synchronization model, and public APIs remain
unchanged by this final pass.

## 5. Controlled Go performance observations

The final review also reran the existing Go 1.27 Linux microbenchmarks with
`GOMAXPROCS=4`, five samples, and no concurrent qualification workload. Key
ranges were:

- Registration event decode: 813-887 ns, 896 B, 12 allocations;
- pending 32-field coalescing: 5.54-6.01 us, 112 B, one allocation;
- Redis clock upper bound: 22.5-24.6 ns, zero allocation;
- 500-record immutable Selector view publication: 52.4-54.2 us, 31,528 B,
  six allocations;
- typed `One(500)`: 11.6-12.6 us, about 2,225 B, 28 allocations;
- typed `Any(8/500)`: 13.1-14.1 us, about 8,065 B, 97 allocations;
- Catalog 4 MiB-boundary shape validation benchmark input: 6.64-6.82 us,
  9,472 B, one allocation;
- Catalog Replace event decode benchmark input: 71.8-79.7 us, 91,485 B,
  eight allocations.

These are same-host implementation observations, not fleet capacity promises.
No code change was accepted solely because it looked shorter or more advanced.

production or stable `1.0.0` release.
