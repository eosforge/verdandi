## Redis / Astra 统一基线

### 本轮整理及验证范围

整理集中于性能执行器和验收边界: 两套公开 SDK 共享参数、记录生成、分组、多写者、可见确认及统计; 独立适配层和进程隔离 OpenSSL/BoringSSL; Python 共用既有真实集群夹具并统一资源采样、失败记录、清理和配对统计. 修复原探针数值先缩窄再校验、尾部字符误接受的问题. 不改生产协议、SDK 调度算法或冻结旧版实现来改善分数.

本轮 16 项定向 Release CTest 通过, 用时 10.72 s: cpp_scene、cpp_origin、cpp_catalog_state、cpp_catalog_replica、cpp_ephemeris_state、cpp_ephemeris_replica、cpp_dispatch、cpp_catalog_fault、cpp_ephemeris_fault、cpp_edition、cpp_ephemeris_rpc、cpp_comet_client、cpp_comet_beacon、cpp_comet_subscription、cpp_comet_selection、cpp_baseline_workload. 后续新增“历史曾见到但最终丢失”夹具后, cpp_baseline_workload 再次通过, 6.29 s. Python 运行器 6 项单元测试在 Windows/Linux 通过; 新负载夹具的 ASan/UBSan/LeakSanitizer 和 TSan 通过. 后两项仅覆盖新负载执行器, 不冒充全系统 Sanitizer 重跑.

实际运行验证原生/Almanac/Comet 探针对负号、尾部垃圾、缩窄溢出的拒绝. 两套适配器均离线 Release 构建成功; 未增加全局软件、依赖或长期任务. 这是一轮有边界的整理与验证, 不声称已经完成全仓生产认证.

### 环境和可比性

- 同一 Ubuntu VM, 16 vCPU, 内存上限 8 GiB; 正式比较期间实际 MemTotal 为 **1.79–4.85 GiB**, 最低采样可用内存约 1027 MiB. 构建按实时内存使用 1–2 并发, 功能测试 2 并发; 性能场景串行, 不与编译或其他测试争用资源.
- GCC 16.2.0, 旧 SDK C++23、新 SDK C++26, Release. 回环网络, 业务认证/TLS 关闭; Astra 真实启动 Pulsar/Polaris/单 Star, 内部准入/TLS 保持启用. Redis 8.8.0 禁用 AOF/RDB, 独占容器每场清空数据, allocator/脚本缓存可延续; Star 每场重新启动. 双方确认都代表当前数据节点内存提交.
- 所有记录均进入轮转写入, 8 个写者各自独占记录序列, 每写者最多一个在途请求. 各范围有独立真实订阅; producers/consumers 各使用指定数量的共享 Client. 流数不等于 TCP 数.
- `receipt`: 等实际提交确认即发下一次; `visible`: 还须全部目标订阅观察到正文. 旧版没有相同的新式回调, 因此共同使用 1 ms 周期扫描公开视图. 可见延迟包含扫描与唤醒, 不能直接与下文的回调探针相除. 两种模式都核验最终版本, 失败不能计入成功吞吐.
- 各配置每轮 5 s、原计划三轮, Redis/Astra 交替先后. 仅同配置同轮双方成功、MemTotal 不变、换页计数不增的样本组成配对汇总. 数字是各轮吞吐/分位数的中位数, 不合并原始延迟样本. `p99.9`、吞吐范围和全部单轮数据保留在原始结果及 summary.json 中; 短窗口不构成 SLA.
- 旧 Registration 更新隐式刷新 TTL, 新 Beacon 的 Data Update 与续租独立; 旧 Catalog 没有新动态 Catalog 的租约. 比较的是应用完成同一操作的实际代价, 不是宣称协议工作量完全相同. 旧 Fields 额外的 `body` 包装、解码也保留在成本中.

执行契约、离线构建和复现命令见 [统一基线](baseline/README.md). 主矩阵 28 配置, 另外 2 个默认合并窗口对照. 由于首个旧 Selector 故障触发早期运行器停止, 后续运行器改为保留负载失败并继续预定场景; 该配置的原始失败也保留, 因而共 **182 个正式样本, 178 通过、4 失败**. 其中 Astra **91/91**, Redis **87/91**; 159 个单侧样本满足内存稳定条件, 实际统计仍要求整对满足条件. 四个失败全部来自同一旧版零合并高负载配置, 不把该配置纳入吞吐对比.

### 结论和故障解释

1. **Astra 当前并未全面快于旧 Redis SDK.** Catalog 单组 8 订阅由 64 增到 256 活跃记录时, 可见完成率约 2687 → 2640/s, 旧版约 4056 → 3819/s. 拆为 4 组后 Astra 提升到约 3901/s. 这里包含公开 View 扫描、SDK 工作和网络成本, 不能直接定位到 gRPC 本身.
2. **低于饱和区间差距较小.** 两域计划 500 次/s 均完成, p99 约 2.36–2.64 ms; 3 s 短租约背景下约 2.35–2.72 ms. 不把低负载接近等同于饱和容量相等.
3. **旧 Selector 有配置相关的稳定性/延迟取舍.** 256 注册、8 Selector、1 共享 Client、receipt、合并窗口 0 ms 在四次正式样本中均出现 `verdandi: unavailable: field selector`, 后三次附加诊断为 `no queued diagnostic`. 日志确认初始化完成、正式写入已经开始, 不能归因于忘记等待初始同步. 精确恢复触发原因尚无 CPU/事件跟踪证据, 不断言必定队列溢出.
4. 恢复旧版默认 10 ms 合并后, 该对照的 12 个样本均通过: 提交完成率 Redis/Astra 约 **12830/3904 次/s**, 而全订阅可见完成率约 **151/2633 次/s**, 可见 p99 约 **56.68/5.46 ms**. 静态代码显示旧 Selector 在检查合并截止后可能进入最长 50 ms 的消息等待, 因此没有后续消息唤醒时, 10 ms 配置并不保证 10 ms 内发布. 这是当前冻结实现的具体行为, 不能概括为 Redis 的固有延迟.
5. **不能用“每次续租广播 Attr/Data”解释本次差距.** 当前 Ephemeris 纯续租已绕开下游 Scene/History/Watch, 来源序列仍负责复制租约; Catalog 的高扇出测试也存在差距. 本轮没有单独测 Renew QPS、序列化占比或网络字节, 不能把总 CPU 分摊为某个未经测量的热点.

### 计时与校验口径

网络窗口每轮 5 s. 完成一次操作必须拿到实际写入回执, 并在每个订阅的推流回调中看到对应版本/正文; SDK 异常数必须为零. `commit` 是回执延迟, `visible` 额外包含来源复制、Watch 编码/传输、SDK 投影和应用通知. 下表延迟使用 **visible**, 各项为稳定轮次中位数, 不是将全部样本合并后重新求分位数. p99.9 仅作短窗口观测, 不视为稳定 SLA.

默认闭环: 每个写者独占热点 Key, 同时最多一个在途请求, 等所有订阅可见再提交下一条. 生产者共享一个 Client, 每个订阅 Star 共享一个 Client; 流数不等于 TCP/文件描述符数. 每个真实订阅均监听全 Scope, 多 Star 情况只有一个来源 Star 接受写入, 其他 Star 通过对等复制接收.

带固定速率的两行从原计划时刻计时, 包含客户端来不及发起的排队, 但仍有每写者单在途限制. 所以表中是 **当前负载模型下的完整链路完成率**, 不代表 Star 单独的最大受理 QPS, 多 Star 行也不是多来源写入的线性扩展实验.

**测量修正:** 首版探针让多个写者反复调用 Subscriber/Observer 读取接口确认可见性, 自身制造共享锁竞争. 最终改用 SDK 推流回调及每写者条件变量, 完整重跑全部 66 轮. 下表只使用最终 `push/` 数据; 早期轮询数据只用于诊断, 不用于容量结论. 生产代码没有因这个修正而改变. 回调仍会点查本次 1..32 个热点, 应用确认开销包含在结果内.

### 资源、优化优先级与未覆盖范围

最终稳定网络样本的所采进程 RSS 总和峰值约 **240.3 MiB**, 出现在 64 KiB Attr/两 Star 场景. 包含探针、Pulsar、Polaris 和 Star, 认证场景还含 Astrolabe, 初始化也在采样范围内. RSS 相加会重复计入共享页且不含 OS/采样器, 不能当作精确物理占用. 测前已有约 79.1 MiB swap 占用, 不等于本轮产生同等换页; 稳定筛选使用计数变化. 20/200 ms 采样也不能替代分配跟踪或长时泄漏验证.

依据本轮数据, 优先级如下, 未修改生产算法来追求未经验证的收益:

1. 优先分析真实推流扇出、SDK 活动调度和线程唤醒. 同样 100 条记录/8 写者, 1 流到 10 流完成率由约 5,854 降至 2,298/s. 这是完整链路成本, 包含应用回调确认; 没有 perf/锁采样, 不能将差值全部归给服务端或某把锁. SDK Core 的活动扫描是静态候选热点, 尚未作因果验证.
2. 大来源恢复与长暂停追赶是已经量到的长操作. 后续可先测并发读写受阻和真实到期数量, 再决定锁外准备或空轮跳跃; 不重新引入会破坏时间语义的截断推进, 也不先泛化存储框架.
3. 现有内存更新是微秒量级, 实际 RPC 可见是毫秒量级. 这支持优先测量调度/推送链路, 不支持直接把全部差值解释为网络/Protobuf 成本. 原生和 RPC 的负载不同, 不能相减作精确归因.
4. 保留单 Key 发布和现有独立续租语义. 本轮没有证明批量 Renew、多目标 Watch 或跨 Key 原子批次是必要的收益点, 不为追求“少 RPC”立即扩大协议面.

仍未覆盖: 10 万/百万条数据、跨物理机网络、多来源同时写入、多精确目标/大量连接、慢消费者和发送预算压力、故障切换中的尾延迟、长时泄漏、完整恢复时的并发锁等待、实际线速字节/分配归因、独立 Renew 规模及完整 B01–B14. Pulsar 本轮是实际服务依赖, 没有单独测其对时容量. 固定分配 8 GiB、独立压测机及重复较长窗口能提高后续容量结论可靠性, 当前不修改 VM 配置或自动启动这些测试.

- 公共 TLS 的证书提供器错误地调用要求根集合初始化的整体校验. 改为解析完整 PEM 链、验证叶证书用途/有效期及私钥匹配后仅安装身份; 信任链及主机名仍由客户端校验, 不伪造客户端信任根. 新用例覆盖无内部准入文件、过期、不匹配、缺失及截断中间证书. 最初尝试空 UpdateRoot 被小范围测试捕获断言, 已撤销该尝试.
- 公开 TLS 夹具缺 SKI/AKI, Python 严格 HTTPS 校验拒绝. 生成器重新计算各标识并更新公开测试证书, 保留过期/错误签名场景; 未改变准入签名密钥或账号, 未关闭严格校验.
- Catalog 半批停滞夹具过早附带实例尾字段, 实际触发协议拒绝. 修正为合法半批后验证首帧/半批超时恢复; 客户端严格协议校验保留.
- Release 优化编译发现 Ephemeris 事件副本的 maybe-uninitialized 诊断. Catalog/Ephemeris 同步改为容器内原地合并, 避免初始共享引用复制和自移动; 新增唯一记录、多组压缩及 Attr/Data 基线用例, 四种配置均通过.
- SDK 独立消费新增 CMake/#embed 公开 CA、显式外部缺失 CA 不回退和关闭公共 TLS 的配置边界, 源码接入与安装包均通过四种配置. 外部 CA 的真实 TLS 握手由 Comet RPC 用例覆盖, 包消费不冒充握手验证.
- ASan 首轮发现 Protobuf 36.1 的 PROTOBUF_MESSAGE_GLOBALS 在插桩源码中自动启用, 而普通预编译库使用另一种 ClassData 布局. 小探针实测普通/ASan 分别为 56/40 字节; 使用上游 PROTOBUF_MESSAGE_GLOBALS_TEMPORARY_OPTOUT 兼容开关后统一为 56 字节. 生成代码和 SDK 消费者均保持相同 ABI, 不关闭 ASan/UBSan 或 has-bit 一致性校验, 完整回归已通过.
- LeakSanitizer 另发现 Core -> Alarm -> 回调 -> Core 引用环, 关闭后最后一份闭包仍保留对象. 回调开始时将拥有权移到本地变量, 覆盖 tick 后释放; 新增 32 次创建/关闭后弱引用必须失效的行为检查, 四种配置及独立包消费均通过. Pulsar 的 Alarm 只捕获独立截止状态, 不回指拥有 Alarm 的 Reactor, 未发现同类环; Go 当前没有这条 gRPC C++ Alarm 路径.
- Admin 原生 fetch 被当作 Api 方法调用, 真实浏览器触发 Illegal invocation. 绑定正确全局接收者并新增行为用例; 修正轨道规划可变 band 的类型及两项已有 Three.js 测试假设.
