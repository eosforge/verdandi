## 三 Star 性能口径

标准配置库现为 36 项; 本轮选取 15 项代表配置, **未重跑全部 36 项**. 包括所有四个新增 2 KiB 场景、匹配的 128 B 对照、1 KiB 载荷及两域 24 写者. 每台 Star 均接受本地写入, 消费端错开节点, 每 Scope 覆盖三台 Star. 生产端与消费端各有 clients 个共享 Client, writers 是写线程总数; 每线程最多一个在途请求.

receipt 测提交回执, visible 等待全部相关订阅观察到该更新. 两者都是闭环吞吐, 不等同固定到达率下的生产尾延迟. 数据先完成初始化, 然后测正式窗口, 最后重新读取全部视图并逐字节验证完整内容. 2K 是包含记录编号/版本的 2048 B 业务正文, 不是完整 RPC 线长; 不启用压缩. 旧 SDK 按真实 Fields 接口编码, 不扣除其额外开销.

对照是同一 VM 总资源下的应用方案, Astra 包含三 Star 复制和控制面, Redis 为单节点且关闭持久化, 不代表同等复制保证的引擎对比. visible 使用两边相同的 1 ms 公开视图轮询, 包含采样和最慢订阅成本, 不是纯网络传播时延. 具体接口与资源差异见 [基线契约](baseline/README.md#明确的差异).

## 较长窗口复核

五秒初测出现两个 1 KiB 配置与两域 24 写者下降, 以及 Ephemeris 高扇出 visible 上升. 对正负两方向共五个配置使用相同二进制再跑三轮二十秒, 不覆盖原样本; 不重复 Redis, 只检验代码前后差异.

## 结论与下一步

- 新增 2 KiB 正文、两域更新/续租、关闭和复制的已测正确性通过. 读端过滤 TTL 的建议未实施, 到期仍提交统一投影版本; 本轮不能用性能结果证明改为惰性读过期的收益.
- 当前所选提交回执场景的 Astra 吞吐均高于 Redis 适配器, 但全部可见场景仍落后; 三 Star 与 SDK 消耗的 CPU 也不同, 不能据此宣称单位资源效率领先. 2 KiB 高扇出的吞吐相较同版本 128 B 下降 10.5% 到 18.5%, 值得优先定位序列化、扇出和客户端视图安装成本, 当前尚无分段剖析确认根因.
- 本次组合优化不能宣称普遍提高吞吐. SDK 的就绪消费从全目录扫描改为 O(K), 但期限/共享状态维护仍 O(N); 多页弱缓存减少相同在途页的重复构造, 不复用 gRPC 最终线编码. 基线只有 9/12 个订阅, 未覆盖数千空闲 Watch 的目标负载, 所以不能据此判定大 N 收益.
- 下一步先增加分段计数: Core 就绪数/目录扫描数、页缓存命中/重新构造次数、提交到远端安装/下行发送/SDK View 安装的时间. 另做大量空闲 Watch 中少数活跃的定向模型和大快照交错读取, 保持三 Star 写入及资源预算. 不先引入新传输层、线程池或更多状态机.
- 若确认普通单页批次占主导, 可评估内联第一页弱槽, 只为第二页以后分配页号索引; 当前 vector 每批次需要额外分配, 这是静态候选, 本轮没有直接证据将其定为退化原因. SDK 与 Star 改动应分别对照, 避免组合成绩掩盖贡献.
