## 保留或回退的对照证据

### Watch 在途索引

使用审查开始时暂存改动中的实际 `WatchQueue` 头文件作为 before, 当前 `Watch` 为 after. **该微基准的 before 不是 HEAD**: HEAD 尚未维护 unordered_set 在途索引, 而是低频扫描拥有目录. 相同预建流、相同入队/弹出/开始写/结束写生命周期, 每规模交替执行六轮, 每轮约一百万次页面循环. 表为每轮结果的中位数, 单位 ns/页.

| 活动流数 | 原 unordered_set 在途索引 | 当前侵入式链 |
| --- | ---: | ---: |
| 16 | 68.38 | 17.62 |
| 256 | 115.53 | 17.86 |
| 4096 | 95.18 | 17.46 |

独立计数产物验证在途索引分配从 **1 次/页降为 0 次/页**; 分配插桩未用于计时. 新方案每条流增加两个指针, 空闲流同样承担约 16 B, 不声称所有负载的总内存一定更少. 此探针隔离调度簿记, 不包含 gRPC、锁竞争和页面构造, 不能把其倍数当成整机 QPS 倍数. 结合生命周期用例和真实 RPC 回归, 保留公共抽取并替换其在途容器.

### 文本字段 string / bytes 编解码

相同 ASCII 实例/Scope 文本、相同 payload 的两份代表消息, 使用同版本 protoc. 每轮复用消息和缓冲, 执行 50 万次序列化+解析, 交替六轮. 两组线字节数完全相同, 不是 UUID 压缩测试.

| Payload | string, ns/往返 | bytes, ns/往返 | 编解码耗时下降 |
| --- | ---: | ---: | ---: |
| 0 B | 195.92 | 117.29 | 40.1% |
| 64 B | 207.04 | 147.88 | 28.6% |
| 2048 B | 322.29 | 267.42 | 17.0% |

因此保留当前 Scope/实例字段的 bytes 迁移, 同时保持业务边界的文本验证. 这项证据只覆盖代表消息的 C++ 编解码, 不含 Go `[]byte/string` 转换、入口校验或整条 RPC, 不宣称系统吞吐提升 17%..40%. UUID 原始 16 字节和 principal 原始 32 字节另有确定的载荷缩减, 其契约与持久格式边界见 [协议](../proto/README.md#消息数据与标识) 及 [Pulsar](../astra/pulsar/README.md#sqlite).

## 最新分阶段性能测量

### 负载与计时方法

- 三 Star 均接收本机来源写入, 跨节点订阅及来源复制开启. 96 记录、3 Scope、每 Scope 12 个订阅、3 个生产 Client + 3 个消费 Client、6 写者, TTL 30 s.
- Catalog 2 KiB; Ephemeris Data 64 B / Attr 256 B. 每次写入等到相关 12 个订阅全部可见后再继续, 闭环不限速, 每样本 20 s. 这不是纯 unary 吞吐或纯网络延迟.
- 每种负载四组 plain/probe 配对, 两次 plain 先运行、两次 probe 先运行. 两配置除诊断插桩外使用相同源码/依赖/参数. 表为每轮统计量的中位数, 不是合并分位数, 也未计算具有统计显著性保证的置信区间.
- 首轮 Ephemeris 夹具运行期间与早期 trace 解析重叠, 在汇总其结果前已明确整对单列, 补充 repeat=4 保持四组平衡对照. 原始两份不利或有利结果均保留, 不按结果选择删除. 其余正式窗口没有同时运行分析程序.
- 所有计时使用同一客体 CLOCK_MONOTONIC. 服务/SDK 阶段按线程、阶段采样 1/8; 业务回执/可见/采样器事件全量记录. 每进程固定 32 MiB 映射, 热路径不写文本、不记录业务载荷. 初次建文件发生于预热/初始化, 正式统计只接受起止均在 20 s 窗口内的事件.
- 独立阶段分布不能相加. `read_to_consume` 与部分 SDK 锁/调度时间重叠; `prepare_page` 不含 gRPC 后续序列化, `write_to_callback` 也不代表客户端安装确认. 阶段计时含线程抢占, 不能将锁等待全部归为持锁代码的 CPU 耗时.

### 结论及下一步

1. **优先排查 Star 下行调度/索引锁.** 就绪队列 p99.9 约 1.65–1.67 ms, 提交通知等待索引锁约 1.01–1.06 ms; 已测 SDK 对象排队约 0.46–0.52 ms. 但队列含写完成/进度通知等合并任务, 不等同于每条业务更新从提交开始的等待.
2. **没有支持优先重写页面准备或 SDK 投影的证据.** 页面准备中位约 2 us, 投影安装中位约 8 us、p99.9 约 80 us. 这不能推出原生 Store、所有编码或大快照均无瓶颈; 这些范围没有全部被此阶段覆盖.
3. **公开视图轮询显著影响可见延迟口径.** 配置为 1 ms, 实测扫描起点间隔中位约 1.12 ms, p99.9 约 2.22–2.40 ms; 扫描本身 p99.9 约 0.72–0.81 ms. 不能把端到端约 9 ms 的 p99.9 全部记为 gRPC 或 Star 的处理时间. 后续保留现有公共对比口径, 另加准确的 SDK 安装时间, 不通过修改轮询偷偷改善成绩.
4. **尚未闭合全部尾延迟来源.** Catalog 最大样本 25.331 ms 位于正式窗口最初 100 ms, 原样保留; 其他时段也有尖刺. 100 ms 同时段各阶段最大值没有逐请求关联关系, 加上 1/8 采样, 不能用它们相加或断言某个阶段一定没有贡献.
5. **下一项最有价值的测量是同一变更的跨 Star 关键路径**: 本地提交 → 来源导出 → 对端接收/安装 → Watch 入队/发送 → 各订阅安装, 标出最后完成的订阅. 同时单独测量持有下行索引锁期间的 StartWrite 调用时长和控制轮各阶段耗时, 才能决定缩短持锁区间还是调整调度配额. 本轮不直接拆锁、加线程、改协议或扩大状态机.

上一轮在途链/全目录扫描对照没有稳定支持回退. 当前保持侵入式在途索引及到期后取扫描锁; 本轮没有新的生产性能改动. 后续新测试仍需当轮授权.
