# Selector 重连剪枝与分层增量同步探索性审核（非实施计划）

日期：2026-09-08。承接 [Selector 简化设计审核](D:/projects/verdandi/registration/selector-simplification-review-20260908.md)。本轮仅分析设计空间；没有修改 SDK、Lua、部署配置或安装依赖。除“当前契约内复用同 UUID 的不可变 Attr”外，本文内容不得直接作为准备实施的任务清单。

## 结论与范围

支持同一 UUID 复用不可变 Attr。请求携带已持有的内容 revision、由服务器裁剪回复，在语义上可行，但需要协议原型和基准证明收益。要让重连时连成员枚举都能省掉，还需要 Registry 级变更游标和可查询的变更信息；这一整套方案复杂度及稳态写入代价较高，当前不进入实施。

当前决策如下：

| 方案 | 复杂度与性能影响 | 当前决定 |
| --- | --- | --- |
| 客户端复用同 UUID 的不可变 Attr | 低；不增加 Redis 写入，只增加受控的本地缓存寿命 | 可随 Service/锁基础重构实施 |
| 显式 Patch 与完整 Update | 中；Patch 保留窄写性能，Update 提供自包含基线，Patch 缺口逻辑仍须封装 | 候选协议，先验证 Service 内有界实现，尚未批准实施 |
| 携带 content revision 的条件读取 | 中；增加读取协议、Lua 分支和兼容路径，可能减少字节及一次往返 | 仅做基准驱动的独立原型，不进入主实现 |
| Registry 游标、变化索引、删除 floor、历史 epoch | 高；每次变更增加 Redis 写入和元数据，切主、TTL、分页与裁剪组合复杂 | 暂缓，不进入当前实施 |
| Data 字段 revision | 高；每次 Update 增加逐字段元数据维护 | 暂不采用 |
| 跨 Registry 全局 revision | 高；增加所有 Registry 共享写路径，却不能单独定位变化 | 当前不采用 |

若以后重新评估完整增量协议，各标识必须按职责区分：

| 标识 | 作用 |
| --- | --- |
| 数据历史 / 重建代号 epoch | 判断旧游标是否属于当前可验证的数据历史；历史不明时重建同步基线 |
| Registry change_cursor | 指出此 Zone/Type 下发生了哪些写入变化，用于成员与实例级增量发现 |
| Service content_revision | 沿用当前单 UUID 内容 revision，判断 Data、应用 Version 等内容是否需要重新传输；不代表租约新鲜度 |
| 可选 Data 字段 revision | 在需要精确字段差量时定位变化的 Data 字段 |

“全局 revision”有两种理解：如果指一个 Registry 内全局游标，加每个实例的 revision，这两层有明确价值；如果还要所有 Zone/Type 的每次写入共同推进一个额外总计数器，当前单 Registry Selector 没有必须使用它的路径。跨 Registry 的总目录确有需求时再设计总游标，不能用总数代替具体变更信息。

历史 epoch 与每次写入递增的全局计数器作用不同。前者用于拒绝跨历史的错误复用，后者只排列写入；不能因为增加两个普通计数器就认为解决了回退和数据分叉。

这里分为当前契约下可做的数据复用，以及探索性的读取/游标协议扩展。后者会改变写入脚本和读取协议，当前明确排除在实施范围之外。

## 1. 不可变数据复用的边界

当前契约明确规定：Attr 和 TTL 在 UUID 生命周期内不可变，Data 与应用 Version 可变；每次新进程注册使用新的 UUID。

依据：[registration/api.md:110](D:/projects/verdandi/registration/api.md:110)、[protocol.md:314](D:/projects/verdandi/protocol.md:314)、[protocol.md:181](D:/projects/verdandi/protocol.md:181)。

因此，缓存身份应至少由 Zone、Type、UUID 和兼容的协议/字段契约确定。断线、重连和切主本身不意味着业务进程重建，不必自动丢弃该实例已经拥有的不可变 Attr 字节及类型投影。

新 UUID、本地已经回收 Attr、协议或编码契约不兼容时必须重新加载。若完整 Register 明确给出了与同 UUID 缓存不同的 Attr，不能静默声称缓存仍有效，应按契约冲突处理或走明确的完整校验路径。

SDK 已经拥有的不可变字节可以共享引用。调用方拥有的可变对象和已返回快照仍遵守独立性约定；“复用 Attr”不意味着保留调用者可能继续修改的对象。

## 2. 请求携带 revision，由服务器裁剪回复

应使用协议 `@revision`。当前 `@version` 是应用定义的内容字段，不能代替同步游标。

如果基准证明值得继续，候选单实例读取请求应包含：UUID、已确认完整的 content_revision、是否持有该 UUID 的不可变 Attr，以及本次读取所绑定的数据历史/同步上下文。未完成或有版本缺口的 Service 不得伪报一个完整基线。

| 服务端判断 | 建议回复 |
| --- | --- |
| 当前内容 revision 与客户端完整基线相同 | 仅返回必要 Meta / 租约信息，省掉 Attr 和 Data |
| 内容已变，客户端有可信 Attr，尚未维护字段级差量 | 返回 Meta 和完整 Data，省掉 Attr |
| 内容已变，字段级版本覆盖客户端基线 | 返回 Meta 和变化 Data 字段，并标明基线及结果 revision |
| 新 UUID、客户端无 Attr，或需要完整重置 | 返回完整 Meta、Attr、Data |
| 已删除 / 已不存在 | 返回明确的缺失状态，不伪造一个可做普通大小比较的内容 revision |
| 历史不匹配或无法证明基线可用 | 返回 reset / 重新建立基线的结果 |

剪枝比较与取回数据必须属于同一次一致读取，不能先读 revision、隔一个网络往返后再把另一个版本的字段标成该 revision。建议考察有明确条目/字节上限的只读单记录脚本或小批次读取，复用现有 Lua 生成和错误模型；不引入一次遍历整个 Registry 的大脚本。

客户端在收到完整内容后复用 Attr 对象只能减少客户端复制和解码；要减少线上传输，服务器必须在生成回复时省掉 Attr。这两类收益应分别测量。

当前 Go/Rust 的同 revision 头部读取属于已有优化，C++ 尚需补齐。新的条件读取可进一步避免“先读头部，发现变化，再读完整内容”的第二次往返。

## 3. 两个计数器仍不能定位变化

客户端看到 Registry 游标从 100 变为 105，只知道发生过写入，不知道是哪个 UUID 改了字段、哪个新增、哪个删除。要返回增量，必须有变更索引或可重放日志。

若将来实测确认完整成员扫描是主要瓶颈，可优先评估**每个 UUID 只保留最新变化位置的索引，加有界删除记录**，因为 Selector 需要恢复最新状态，不要求还原每一次中间操作。相比保存所有事件，这种结构可以合并同一实例的反复更新；若改用日志，应明确额外历史空间和裁剪规则，不同时维护多套没有必要的历史结构。当前没有这项性能证据，因此不进入实现。

这种方案要求每次有效 Register、Update、Renew、Unregister 在原有写入脚本中同时维护 Registry 游标、对应 UUID 的最新变化位置，以及必须的存活/删除信息。Data、索引、游标及通知必须保持一致；需要在发生写入之前完成类型、容量和边界预检。这会增加稳态写放大和 Lua 执行时间，尤其 Renew 的频率通常远高于重连，不能为了偶发重连优化而默认增加所有续租的成本。

显式 Unregister 的删除记录需要保留一段有界历史。维护 `minimum_supported_cursor`：客户端游标早于可支持范围，返回 reset，不能回复“没有变化”。正常合并同 UUID 的旧变化不一定丢失最新状态信息；实际淘汰仍可能影响旧客户端的信息时，必须相应推进可支持范围。

游标元信息不能跟某个实例的租约一起到期。Registry 清空、重建或相关索引丢失时，要能够识别新 incarnation；不能重新从同一个数值起步后把旧缓存误认成新状态。数值范围、溢出和索引排序精度也必须按统一协议处理。

## 4. Registry 增量与 Data 字段增量分层

Registry 索引回答“哪些 UUID 需要关注”；Service content_revision 回答“该 UUID 的内容是否需要传”；要知道它具体哪些字段需要传，还需字段级变更依据。

现有 Catalog 已实现相近机制：[read.lua.inc:95](D:/projects/verdandi/lua/src/catalog/actions/read.lua.inc:95)根据本地 revision 返回 unchanged、patch 或完整内容，配有字段版本与完整替换边界；[delete.lua.inc:62](D:/projects/verdandi/lua/src/catalog/actions/delete.lua.inc:62)维护删除信息裁剪后的 floor。

Registration 可以借鉴这些条件读取和测试思想，但更简单的候选是每次 Update 都携带完整应用 Version/Data。这样已知 UUID 的较新 Update 自身就是可变内容基线，不需要给每个 Data 字段维护 revision，也不要求补齐中间 Update。Attr/TTL 继续按 UUID 复用；未知 UUID 仍需完整读取。

字段版本索引增加每次有效 Update 的写入工作和元数据空间，当前不采用。候选协议改为两个显式操作：完整 Update 增加 Redis HSET、Pub/Sub 和 Selector 字节成本，但可直接形成基线；Patch 保留窄写优势，只在已有连续基线上直接应用。两者共用同一个 content revision，且不根据载荷大小自动改变语义。这里重建正确当前状态，不提供完整历史事件回放。

## 5. 续租和自然过期必须单独说明

内容 revision 不随 Renew 增长，但 timestamp/deadline 会变。Registry 游标若用于恢复完整可见状态，就需要让 Renew 也推进该游标，并更新该 UUID 的最新变化位置；回复可以只带租约元数据，不必重传 Attr/Data。这项要求正是当前暂缓该方案的主要性能原因之一。

若为了减少写入而选择不索引 Renew，重连时就必须补做租约元数据校验；不能同时宣称 Registry 游标没变就能跳过全部检查。断线超过普遍续租间隔时，即使内容几乎不变，很多 UUID 也需要更新租约信息，这是实际状态变化，无法由计数器消除。

自然 TTL 到期不执行项目自己的 Unregister 脚本，因此不会自动推进自定义游标。方案需要：从已覆盖的 Register/Update/Renew 恢复最新 deadline，重新校准 Redis 时间，然后处理本地到期及 retained。即使 Registry 写入游标相同，时间推进也可能使选择结果变化。

不能依靠 Redis keyspace 的 expired 通知充当可靠删除日志：它沿用 Pub/Sub 的交付边界，事件发生时间也不保证等于 TTL 到零的时刻。[Redis 过期通知文档](https://redis.io/docs/latest/develop/pubsub/keyspace-notifications/)

## 6. 主切换下的版本相等可能只是数值碰巧相等

例如旧主已到 Registry 游标 100，客户端据此缓存 A；新主只复制到 98，随后接受两次不同写入又到 100。数值重新相等，内容却不同。再增加一个同样存于该异步复制数据集的全局计数器，不能消除这个问题。

增量请求因此需要绑定可验证的数据历史及 Registry incarnation。epoch 不能只是一个会一起回退、却从未因历史变化失效的 Redis 计数器。

Redis replication ID 用于标识数据历史，副本提升会产生新的 ID，提供了可研究的历史识别依据；它和复制 offset 不能直接替代业务 Registry 游标，也不能仅凭地址、连接重建或进程标识作同样推断。[Redis replication ID 文档](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

具体历史标识的获取、权限、主角色确认及读取/订阅绑定仍需形成协议实现。第一版采用保守边界：无法证明历史连续、发现切主/回退、Registry incarnation 改变或历史裁剪超过游标时，reset 并重新发现成员。即使需要 reset，同 UUID 的不可变 Attr 仍可复用，Data 也按权威内容 revision 做条件读取。

## 7. 有效游标下的重连流程

1. 先建立并确认订阅，绑定当前数据历史；保留缓存 Service，但此时不对外宣称已经 Ready。
2. 读取 Registry 的历史标识、可支持游标下界、当前上界 H 及 Redis 时间依据。
3. 若客户端缓存是完整基线，历史匹配且游标可用，仅查询上次游标到 H 的变更 UUID；否则进行成员枚举，复用仍可用的实例内容。
4. 每个变更 UUID 优先用 SUB 完善，仅对仍缺信息的 Service 发条件读取，按版本和身份规则合并结果。
5. 处理本轮订阅栅栏及缺口，校准过期状态，在覆盖到 H 后保存该游标并发布 Ready。

不能只保存“见过的最大游标”：部分读取失败或某个 Service 尚有缺口时，最大值不证明前面的状态已经完整处理。中途失败不能把尚未完成的 H 作为下一次增量基线。

采用可变的最新变化索引时，分页也不是固定快照。某 UUID 的分值在翻页期间移到 H 之后，必须由已建立的订阅路径接管；页内去重、遍历进度、裁剪期间的 floor 复查和最后栅栏都要配套。否则会发生索引和订阅两边都漏掉该实例的问题。

普通 Pub/Sub 断线恢复本身不能补历史；本节允许跳过完整成员枚举的前提，是新增的变更索引/历史协议已经完整实现并通过验证。不能仅在旧协议上增加客户端游标字段就使用这个快路径。

## 8. 全局游标是否值得增加

对于只选择一个 Zone/Type 的 Selector，Registry 自己的游标已足够。额外 Zone 全局计数器会让各 Registry 写入共同维护一个值，并增加写入与复制工作；实际吞吐影响需要测量，不能仅凭存在共享计数器就声称一定形成明显瓶颈。

只有需要跨多个 Registry 一次查询“哪些 Registry 变化了”的总目录时，再考虑总游标与 Registry 变化索引。单独的全局数字仍不足以定位 Registry；它也不能替代历史 epoch、删除保留或字段级差量。

## 9. 进入实现前的性能门槛

完整增量协议只有在现有 HSCAN/条件回读被实测为重连主要瓶颈时才值得重新开启。应先用冷启动、短断线、长断线、热点更新和切主场景记录当前基线：重连传输字节、Redis 命令数、Ready 延迟，以及 Register、Update、Renew 的吞吐和尾延迟。

后续原型不得直接替换当前路径，必须能够独立开关和回退。只有同时满足以下条件，才可提出进入实现：

- 重连的传输量、命令数或 Ready 延迟有足以覆盖协议复杂度的稳定改善；不能只展示构造性的最优案例。
- Register、Update、特别是 Renew 的吞吐和尾延迟没有不可接受的退化，Lua 单次执行时间保持有界。
- 每个实例与每个 Registry 的额外 Redis 内存可计算、可配置、可裁剪，不随运行时间无界增长。
- TTL 自然过期、显式删除、历史裁剪、分页并发更新和 Sentinel 切主均有确定性测试；任一历史关系不明时可以可靠退回完整同步。
- 所有发布语言可以原子维护同一协议；混用旧发布端时不会悄悄漏记变化。

在这些测量完成前，文中的 Registry 游标、变化索引、历史 epoch 和字段 revision 都是被记录的备选设计，不是待办事项。

## 10. 若以后采用协议扩展时的跨语言范围

若性能门槛成立，这仍是协议扩展，不是只调整 Selector 的内部类：

- Go、Rust、C++ 发布端及其共享 Lua 必须一致维护游标、变化索引和可覆盖范围；C ABI、Legacy、C# 复用原生端变化并分别验证绑定行为。
- 只读条件请求、回复状态、精确整数范围、ACL、脚本生成和协议向量需要同时定义；新旧发布端混写时不能遗漏旧客户端产生的变化，无法保证时禁用增量快路径或明确隔离协议范围。
- Lua 的比较与读取必须得到一致记录；客户端票据还要拒绝迟到的旧连接、旧 Service 或旧删除状态，且保留快照独立性和预测事务规则。
- 必测同 UUID 重连 Attr 引用复用、新 UUID 加载、revision 相同但租约变化、字段差量基线太旧、显式删除裁剪、自然过期、分页中索引位置移动、部分失败不能推进游标，以及主切换后同数值不同历史。
- 比较冷启动、短断线、长断线、切主和少量字段更新的字节数、命令数、恢复时间、写入额外开销、索引大小与 Selector 内存。

当前确定范围只保留 Service/锁与同 UUID Attr 复用。显式 Patch/完整 Update 是下一项候选协议：只允许单一 content revision 和 Service 内有界 Patch 窗口，先验证后再决定实施。条件读取可以随后单独评估。Registry 游标、有界变化索引、字段级 revision 和跨 Registry 总目录不进入当前实现。新增协议必须对应实测省掉的工作，不能仅把复杂度从客户端转移到 Redis 或网络层。
