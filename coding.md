# Verdandi Coding and Comment Standard

## 1. Scope and Source of Truth

Verdandi follows the standard idioms and official formatters of each
implementation language. This document defines cross-language quality,
resource, API, testing, documentation, and comment expectations. It does not
invent a common syntax or formatting dialect.

For any SDK:

1. the language's official formatter is authoritative;
2. compiler and standard linter warnings are treated as errors in CI;
3. tests run from that SDK's own package root;
4. language configuration stays under `sdk/<language>`; and
5. an additional language must document its exact verification commands before
   production code is accepted;
6. newly written or modified handwritten source uses 160 columns as the
   repository line-wrap limit; and
7. every source write is followed by the owning language formatter before
   compilation, linting, or tests.

The 160-column limit is an upper bound, not a requirement to fill every line.
Official formatters remain authoritative and may wrap earlier for syntax or
readability. Generated byte-exact artifacts, URLs, commands, and indivisible
protocol/test literals may exceed the limit when splitting would change their
meaning. Do not mass-reflow unrelated source solely to adopt this rule; apply
it whenever a handwritten file is created or materially edited. The root
`.editorconfig` exposes the same limit to compatible editors.

Repository-wide protocol behavior is owned by schemas, Lua, and conformance
vectors, not by whichever SDK is implemented first.

Language and runtime evolution is part of implementation review. Before adding
a custom abstraction, review the language, standard library, compiler, and
selected async/runtime features available in both the SDK's declared minimum
toolchain and the current stable toolchain. Raising the minimum version is an
explicit compatibility decision; adopting an available stable feature is
preferred when it makes ownership clearer, removes work or allocation, or
improves compiler-enforced safety without weakening the supported contract.

## 2. Cross-Language Code Style

- Use conventional language naming and file organization.
- Standardize protocol behavior, observable lifecycle, limits, and errors
  across SDKs; do not standardize their internal code shape. Each SDK uses its
  language's native ownership, cancellation, concurrency, generic, error, and
  resource-management mechanisms.
- Do not transpose a Go Context/channel/interface pattern into Rust, a Rust
  token/trait/RAII pattern into Go, or either SDK's implementation structure
  into Lua merely to make source layouts resemble one another.
- Prefer the formatter's compact single-line form while it remains clear and
  within 160 columns; do not vertically expand short signatures or argument
  lists merely to preserve a narrower historical width.
- Keep visibility at the narrowest useful scope. Items are private by default
  and become public only for a real external caller.
- Prefer one narrow public operation over convenience helpers, option surfaces,
  and exported defaults that expose implementation choices.
- Split modules/packages by ownership and responsibility, not arbitrary line
  count.
- Prefer clear concrete types until multiple real implementations require an
  abstraction.
- Represent validated and lifecycle states in the type system when it remains
  simple and idiomatic.
- Domain lifecycle APIs keep serialization and task-runtime types behind
  private adapters. Go's root transport intentionally exposes its borrowed
  concrete `*redis.Client` for language-native integration and child-domain
  reuse; this is an explicit escape hatch, not a cross-language protocol API.
  Metrics/history belong to the separate synchronizer service.
- Avoid allocation, copying, boxing, reflection, dynamic dispatch, and generic
  abstraction in hot paths unless ownership or measurement justifies them.
- Do not perform blocking I/O, Redis access, or unbounded work on Selector read
  paths.
- Generated source identifies its generator and canonical input. Never edit
  generated output manually.

## 3. Public API Rules

Official SDKs expose the same concepts and stable errors while using idiomatic
language shapes. They must not force one language's conventions on another.

- Public domain names describe Verdandi behavior. A language-specific root
  transport capability may name its selected Redis client only when its
  ownership and ACL bypass boundary are explicit.
- Public configuration uses explicit units, bounded ranges, and secure
  defaults.
- Every configuration field comment states its default, accepted range, and
  zero/nil meaning when applicable. Private normalized runtime-configuration
  fields state the effective default and range they carry. Configuration
  validation methods put a concise comment before each logical check group so
  topology, timing, capacity, relationship, and resource checks are reviewable
  without decoding one compound boolean expression.
- Cancellation and shutdown behavior is part of the contract.
- Caller-owned callbacks state threading/concurrency, reentrancy, panic/exception,
  deadline, and retry behavior.
- Byte ownership and mutation rules are explicit. Do not retain caller buffers
  without a documented contract.
- Collections returned as immutable views cannot be mutated through hidden
  aliases.
- Application Attr/Data types own their field encoding and decoding. SDKs do
  not generate consumer business types or conversion logic; raw Fields use the
  same generic lifecycle APIs.
- Stable errors are machine-readable; diagnostic strings are bounded and not
  used for program decisions.
- Compatibility-sensitive serialized fields and string status values are
  changed only through the protocol review process.

## 4. Errors, Panics, and Exceptions

- Invalid configuration, network failures, malformed protocol data, overload,
  cancellation, and consumer rejection return structured errors; they do not
  panic or crash the process.
- Panics, assertions, or exceptions that escape public control flow are
  reserved for proven programmer invariants, never untrusted input.
- Check numeric conversion, count, length, offset, and allocation arithmetic
  before use.
- Treat decompression, recursion, collection growth, and diagnostic formatting
  as attacker-controlled resource paths.
- An ambiguous Redis write returns a distinct reconciliation error; do not
  blindly retry a non-idempotent semantic action.
- Cleanup is deterministic and idempotent. Cancellation releases permits,
  tasks, timers, connections, subscriptions, buffers, and callback ownership.
- Preserve the original stable error category across language and driver
  adapters without leaking credentials or raw backend messages.

## 5. Concurrency and Resource Style

- Every task/goroutine, channel, queue, permit, connection, timer, and retry
  loop has one visible owner and a bounded lifetime.
- Prefer structured concurrency provided by the selected language and runtime.
  Do not add a permanently waiting goroutine or task when cancellation can be
  observed by an already owned loop or propagated by a native parent-child
  primitive.
- Use bounded queues and channels. An unbounded structure requires explicit
  maintainer approval plus evidence that external input cannot grow it.
- Do not hold a blocking mutex across an async suspension or a potentially
  blocking callback.
- Document lock ordering and atomic ordering when they are not evident
  locally.
- Fence callbacks and I/O completions by connection/subscription generation so
  stale work cannot update current state.
- Make repeated close, cancel, resubscribe, renew, and republish operations
  idempotent.
- Apply global retry admission and jitter to prevent synchronized reconnect
  storms.
- Resource ceilings and backpressure are correctness constraints, not optional
  performance tuning.
- Selector read paths consume an already published immutable local view and do
  not wait for Redis, allocation-heavy rebuilds, or global mutable locks.

## 6. Standard Comment Language and Placement

Until the maintainer declares the complete unpublished tree release-ready,
handwritten production-source comments and API documentation inside source
files use detailed Chinese. This temporary review phase exists so every
parameter, result, error, lifecycle boundary, and non-obvious implementation
block can be audited directly by the maintainer. Test source is excluded and
must not be mechanically translated or rewritten for comment consistency.

The release-readiness pass converts these production comments to concise
standard English so all SDKs and external contributors share one technical
vocabulary. Generated artifacts are changed only through their canonical
source/generator; duplicated generated copies are never edited by hand.

Comments go immediately above the declaration or logical block they explain.
Avoid long trailing end-of-line comments. Struct/record field comments are
placed immediately above their field.

Use the language's standard forms:

- Go: declaration comments for exported API, `//` block comments, and standard
  package documentation.
- Rust: `//!` for module purpose/invariants, `///` for caller-visible contracts,
  `//` for non-obvious implementation blocks, and `// SAFETY:` immediately
  before every `unsafe` block.
- Schema languages: comments describe wire meaning, units, validity, security,
  and compatibility; generated-language wording is not edited downstream.
- Future languages: record the official documentation syntax in this file or a
  linked SDK standard before implementation.

Normal prose comments use complete sentences and punctuation. Short labels may
omit terminal punctuation when they are not sentences.

`TODO` denotes a concrete follow-up whose current behavior is correct but
incomplete. `FIXME` denotes known incorrect behavior. State the resolution
condition and include an issue identifier when one exists. Do not use either as
a substitute for an unresolved security or correctness decision.

## 7. What Comments Must Explain

Comment information that code cannot express clearly:

- every production function's parameters, result, error behavior, ownership,
  cancellation, and lifecycle contract, omitting only facts that truly do not
  apply;

- why subscribe-before-read ordering is required;
- paginated Registry subscribe/scan/PING and Catalog Hash/ZSET/Read/floor
  reconciliation invariants;
- Registration identity and revision fencing invariants;
- why a retry is safe or requires reconciliation;
- lease-deadline and clock-skew reasoning;
- task, connection, timer, buffer, permit, and callback ownership;
- backpressure and bounded queue/snapshot reasoning;
- lock/atomic ordering;
- Redis field/scalar encoding, hashing, and ACL trust boundaries;
- Redis/Sentinel failover behavior that differs from ordinary reconnect;
- consumer activation and atomic local-view publication;
- trust-boundary transitions and secret-redaction obligations;
- intentionally chosen measured optimizations; and
- compatibility behavior that must match other SDKs.

Do not:

- restate the function name, branch, loop, or assignment in English;
- narrate every statement;
- use comments to compensate for unclear names or oversized functions;
- preserve dead code in comments;
- insert speculative future architecture into production source;
- claim code is safe, lock-free, faster, or bounded without naming the
  relevant invariant or evidence; or
- duplicate a rule across every call site when one owning abstraction can
  document it once.

## 8. Comment Density

Verdandi has no numeric comment-to-code ratio. Comment density is driven by
information value:

- Simple single-flow functions normally need no implementation comment.
- Every production function still has one declaration-level contract comment;
  the simple-function exception applies only to comments inside its body.
- A function with distinct non-obvious phases receives one concise comment at
  each real logical boundary, not one comment per statement.
- Public contracts document behavior, errors, cancellation, limits, ownership,
  and security obligations that a caller cannot infer from the signature.
- Security, concurrency, lifecycle, resource-bound, protocol-compatibility, and
  unsafe invariants are always documented when not enforced or evident
  locally.
- Repeated comments are consolidated at the abstraction, schema field, or
  configuration option that owns the rule.

The review question is: can a capable maintainer understand every important
non-obvious constraint without rediscovering it from Redis behavior, another
SDK, or a failure test?

## 9. Go Requirements

The minimum verification baseline is run from `sdk/go`:

```text
gofmt verification
go vet ./...
go test ./...
go test -race ./...
```

Exact commands and any additional standard analyzer are recorded when the Go
module is created.

Go-specific rules:

- Run `gofmt` immediately after every Go write. Because `gofmt` does not impose
  a column limit, manually break only lines that exceed 160 columns or whose
  structure is materially clearer when split; never fight `gofmt` output.
- Accept `context.Context` as the first argument for operations that can wait,
  perform I/O, or be cancelled. Do not store a Context in `Client` or another
  long-lived struct; create it in the owning call or worker scope and pass it
  explicitly. Never derive an object's lifetime from the Context used only to
  open or initialize it.
- The scope that calls `context.WithCancel`, `context.WithTimeout`, or
  `context.WithDeadline` owns the returned `CancelFunc` and calls it on every
  path unless ownership is explicitly transferred. A struct may retain the
  CancelFunc for work it owns, but must not expose cancellation authority to a
  child or caller.
- Use an owner-closed receive-only channel or another purpose-built primitive
  for a long-lived object's shutdown broadcast when storing Context would be
  required solely to obtain `Done()`. Apply operation timeout to each command,
  never to the entire Client lifetime.
- Avoid a dedicated goroutine whose only purpose is to translate one shutdown
  signal into another. Existing owner loops should select the shutdown signal;
  use callbacks such as `context.AfterFunc` only off hot paths and only when
  their asynchronous callback and cleanup ownership are explicit.
- The owner of a goroutine also owns how it stops and is joined or observed.
- Close channels only from the sending owner; do not use channel closure as an
  undocumented broadcast convention.
- Protect maps from concurrent mutation and avoid slice/map aliasing across
  immutable public views.
- Wrap errors with stable Verdandi categories without string matching.
- Export the smallest useful API. Exported declaration comments describe the
  caller contract rather than repeating the name.
- Put each struct field comment immediately above the field; do not use
  trailing field comments.
- Avoid `init` and package-global mutable state unless the lifecycle genuinely
  requires it and tests can isolate it.
- `verdandi-refgen` is an optional mechanical Selector facade generator, not a
  codec or policy generator. It emits callback-scoped read accessors, Data
  setters, mutable-slice clones, concrete type aliases, and the wrapper
  constructor; application `Encoder`/`Decoder` methods remain the sole wire
  authority.
- Generated reference paths use emitted code rather than reflection, never
  expose a mutable Attr/Data pointer, copy slice getters/setters at the public
  ownership boundary, reject field forms whose alias safety cannot be proven,
  and include exact regeneration plus stale-output tests.
- Reference Candidates and their generated views are synchronous callback
  borrows. Go cannot enforce their lifetime statically; runtime transaction
  tokens fence Selection validation and generated Editors, while the read hot
  path relies on the documented no-retention/no-asynchronous-use contract.
- A typed full Data value may be the ergonomic Update input, but the shared
  writer must still compare canonical fields and transmit only changed
  top-level values.

## 10. Rust Requirements

The minimum verification baseline is run from `sdk/rust`:

```text
cargo fmt --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
```

Rust-specific rules:

- Run `cargo fmt` after every Rust write. Rustfmt may choose structural breaks
  below 160 columns; its stable output remains authoritative. Every independent
  crate keeps `max_width = 160` in its crate-local `rustfmt.toml`.
- Follow standard naming: `snake_case` for modules/functions/fields,
  `UpperCamelCase` for types/traits, and `SCREAMING_SNAKE_CASE` for constants.
- Keep imports explicit and visibility narrow.
- Keep Rust test implementations, fixtures, and test-only declarations under
  `sdk/rust/tests`. A production module may retain only a minimal
  `#[cfg(test)]` path hook when white-box access to private implementation is
  required; do not widen production visibility for tests.
- Do not use `unwrap` or `expect` on untrusted input or fallible runtime work.
  Tests and locally proven programmer invariants may use them when obvious or
  documented.
- Do not hold a blocking lock across `.await`.
- Async tasks are cancellation-safe and joined by their owning object. Under
  Tokio, use an owner-held `CancellationToken` and `child_token()` for one-way
  parent-to-child lifetime propagation; cancelling a child must not cancel its
  parent. Cancellation requests do not replace awaiting owned task completion.
- Create cancellation tokens at real owner/task-tree boundaries, not for every
  Redis command. Bound an ordinary operation with `tokio::time::timeout` or an
  equivalent cancellation-safe `select!` branch so the hot path does not build
  an unnecessary token tree or spawn a watcher task.
- Use `# Errors`, `# Panics`, and `# Safety` documentation sections only where
  applicable; do not add empty boilerplate.
- Every `unsafe` block has a directly preceding `// SAFETY:` comment explaining
  why every obligation holds at that location. Every `unsafe fn` documents
  caller obligations.
- Prefer safe code unless measured performance or required foreign interfaces
  justify `unsafe`.

## 11. C++23 Requirements

The normal Windows/Linux developer entry points are `sdk/cpp/build.ps1` and
`sdk/cpp/build.sh`; their complete contract is documented in
[`sdk/cpp/BUILD.md`](sdk/cpp/BUILD.md). They build only the C++23 core, C ABI,
and Legacy consumers. Go, Rust, and C# remain independent source SDKs and use
their own language-native commands; C# loads the separately produced shared
runtime from its application output.

The focused CMake preset baseline is run from `sdk/cpp`:

```text
cmake --preset gcc-debug
cmake --build --preset gcc-debug
ctest --preset gcc-debug --output-on-failure
cmake --build --preset gcc-debug --target verdandi_cpp_clang_tidy
cmake --preset gcc-asan-ubsan
cmake --build --preset gcc-asan-ubsan
ctest --preset gcc-asan-ubsan --output-on-failure
```

C++-specific rules:

- The Windows/Linux build entry scripts treat console text as an operator and
  CI contract. Every script-owned help line, selected setting, tool path and
  version, command, warning, error, elapsed-time result, and final summary uses
  detailed standard English. Temporary Chinese maintainer comments remain
  source-only and must never leak into runtime output.
- The official SDK requires C++23. Public failure-returning operations use
  `std::expected` and do not require callers to catch implementation-driver
  exceptions. Exceptions raised by Boost, allocation, or application codecs
  are translated at the nearest Verdandi boundary.
- Run `clang-format -i` with `sdk/cpp/.clang-format` after every handwritten
  C++ header or source write. The repository limit remains 160 columns, while
  formatter output is authoritative below that limit.
- Public headers expose only the C++ standard library and Verdandi types.
  Boost.Redis, Boost.Asio, OpenSSL, and yyjson remain private implementation
  dependencies behind PImpl or source-only declarations.
- Prefer RAII, `std::jthread`, `std::stop_token`, scoped locks, concepts, and
  immutable value snapshots. Every background task has one owning object, one
  stop path, and a deterministic join before owned state is destroyed.
- Do not hold a mutex while executing application callbacks, waiting for Redis,
  joining a task, or performing file I/O unless the protected invariant
  explicitly requires it and the wait is bounded.
- Schema declarations use the reviewed `VERDANDI_SCHEMA` field descriptors.
  C++23 `consteval`, concepts, and fold expressions validate wire names and
  expand encode/decode calls; runtime reflection and per-value field lookup are
  not introduced.
- Templates remain at the typed Fields boundary. Redis transport, protocol
  state machines, synchronization, persistence, and lifecycle are compiled
  implementation code rather than duplicated per `Attr`/`Data` type.
- The lower-standard boundary is C ABI v1 over the same compiled C++23
  implementation. No STL container, exception, `std::string`, template type,
  application `Attr`/`Data`, or allocator ownership crosses that ABI. Existing
  public structure layouts and signatures stay fixed within one ABI version.
- C11 and direct C++11/14/17 consumer compile tests link through `verdandi::c`;
  idiomatic lower-standard C++ tests link the header-only `verdandi::legacy`,
  which itself links `verdandi::c`. Neither path inherits `cxx_std_23`.
  Static and shared builds are both required; a source build may still require
  C++23 for the internal core target.
- Production builds enable strict warnings as errors for project-owned code.
  Third-party warning policy is isolated from Verdandi targets.
- New public declarations and non-trivial logical blocks follow the repository's
  temporary detailed Chinese-comment review policy; tests do not require
  Chinese comments. Release preparation converts production comments to concise
  standard English in one explicit review pass.

## 12. C# Requirements

The minimum verification baseline is run from `sdk/csharp`:

```text
dotnet format Verdandi.slnx --verify-no-changes
dotnet build Verdandi.slnx --configuration Release
dotnet run --project tests/Verdandi.Tests --configuration Release --framework net8.0 --no-build
dotnet run --project tests/Verdandi.Tests --configuration Release --framework net10.0 --no-build
```

C#-specific rules:

- The managed SDK targets .NET 8 and .NET 10 and is compiled with the pinned
  .NET 10 SDK and C# 14. Nullable reference types, deterministic builds, .NET
  analyzers, and warnings-as-errors remain enabled for every target.
- Public declarations use XML documentation comments. Handwritten production
  implementation blocks use `//` comments only for non-obvious ownership,
  interop, callback, lifetime, or allocation invariants. The repository's
  temporary detailed-Chinese review policy applies to both forms; test source
  remains excluded.
- The C# layer is an idiomatic managed facade over C ABI v1, not another Redis
  protocol implementation. `LibraryImport` owns source-generated P/Invoke,
  `SafeHandle` owns every native handle, and managed owner references preserve
  the C ABI release order even when public wrappers are disposed early.
- Unsafe code stays inside the private interop boundary. Every pointer is
  borrowed for one synchronous call or copied into managed ownership before
  that call returns. No pointer, borrowed Selector candidate, callback view, or
  native error buffer crosses the public API.
- Application Attr/Data/Catalog types implement the static generic
  `IFieldValue<TSelf>` contract. Encoding and decoding use explicit flattened
  Fields; runtime reflection, implicit JSON record values, dynamic invocation,
  and SDK code generation are not introduced.
- Selector policies are synchronous and allocation-aware. The borrowed
  candidate view cannot escape the callback, callback exceptions become stable
  Verdandi errors, and the wrapper never runs a blocking C ABI operation on
  `Task.Run` merely to expose a misleading asynchronous signature.
- `Dispose` performs best-effort deterministic cleanup and never replaces a
  result-bearing `Close`/`Unregister` operation when the caller needs to observe
  failure. Repeated close and dispose remain safe.
- Native binaries are resolved from an explicit
  `VERDANDI_NATIVE_LIBRARY` path, a NuGet-style RID native directory, the
  application directory, or the operating-system loader. Package release must
  include and qualify the matching C++ runtime for every advertised RID.

## 13. Python Testkit Requirements

Python test harnesses are formatted from the repository root with:

```text
python -m black --config testkit/pyproject.toml testkit
python -m black --config testkit/pyproject.toml --check testkit
```

Python-specific rules:

- Black is authoritative for handwritten Python under `testkit`; its committed
  configuration uses a 160-column line length.
- Keep subprocess, remote command, and fixture ownership explicit. Formatting
  must not split or reconstruct shell/ACL/protocol literals in a way that
  changes their bytes.
- Run the formatter immediately after every Python write, then perform a syntax
  or focused behavioral check without creating repository-local cache output.

## 14. Schema and Lua Requirements

- Schema fields document units, legal range, owner, optionality, security
  meaning, and compatibility behavior where relevant.
- Never reuse a removed serialized field or stable status value with a new
  meaning.
- Canonical encoded bytes and hash inputs are generated from one reviewed
  definition and frozen in vectors.
- Registration Lua common logic and action logic are maintained as fragments
  selected by one explicit manifest. Generated operation scripts and SDK copies
  are never edited directly; deterministic generation and byte-exact freshness
  checks are required in the same change.
- Protocol-v1 SDK-to-Lua controls use the operation's documented fixed value
  positions; do not reintroduce a per-call control-name map. Dynamic Attr/Data
  keep canonical named field/value pairs. Any incompatible positional change
  requires a new script/SHA and compatibility text.
- SDKs validate and decode request shape, protocol/kind, identifiers, canonical
  scalars, reserved fields, immutable Attr/TTL, field capacities, and complete
  projected state before Redis I/O. Registration Lua must not duplicate those
  checks.
- Lua may guard only preconditions that require current Redis state or are
  necessary to execute the atomic Redis operation safely: existence, revision
  order, Redis timestamp/deadline, and unusable stored lease metadata.
- Scripts perform bounded work and never scan an unbounded namespace or fleet.
- A hot-path Lua rewrite requires same-fixture Redis server-time evidence and
  complete contract, SDK, race/fuzz, load, and failover regression testing. Do
  not trade away Redis-owned time, revision ordering, matched expiry, atomicity,
  named replies, or self-describing events for a microbenchmark.
- Scripts return stable string protocol results, not numeric enums or human backend
  messages used as program logic.
- The operation-script set has direct real-Redis tests for
  Register/Update/Renew/Unregister, idempotency, stale/gapped revision,
  membership repair, matched expiry, SDK-validation bypass boundary, and
  independent script-cache reload. SDK tests own invalid-input and capacity
  coverage.

## 15. Tests and Benchmarks

- Unit tests name the scenario and expected result.
- Table/vector tests use shared fixtures where protocol behavior is involved.
- Every decoder has boundary, malformed, oversized, and fuzz/property coverage
  appropriate to the language.
- Concurrency tests include cancellation, reconnect, shutdown, generation
  fencing, paginated mutation/replay races, cleanup ordering, and stale
  completion/token races.
- Integration tests use real Redis for Lua, TTL, Pub/Sub, replication, and
  Sentinel failover.
- Cross-language tests prove producer/consumer combinations, not only
  same-SDK round trips.
- Benchmarks record environment and measure CPU, allocations, memory, latency,
  recovery, and overload. Do not optimize from an unverified benchmark or make
  unsupported fleet-size claims.
- Performance-sensitive Go and cross-platform results should be verified on
  Linux/WSL when they affect design decisions; native Windows results are
  useful smoke evidence only.

## 16. Configuration and Secrets

- Configuration fields state units, range, default, operational effect, and
  security impact at the owning definition.
- Production security is not disabled by an implicit zero value.
- Credentials use secret-capable types or providers where practical and are
  redacted from formatting/debug output.
- Do not commit credentials, private keys, recovery codes, environment files,
  Redis dumps, local IDE state, or generated secrets.
- Test credentials are obviously non-production and scoped to isolated
  fixtures.

## 17. Review Checklist

- Standard formatter, compiler/linter warnings, unit tests, and language race
  or concurrency checks pass.
- Public API remains narrow and idiomatic. Any exposed backend type is the
  explicitly documented Go root transport escape hatch, never a domain API or
  an accidental implementation leak.
- Protocol changes update schemas, Lua, vectors, compatibility text, and every
  official SDK in one reviewed change.
- Untrusted input cannot panic, overflow, allocate without bound, or expose
  secrets.
- Every task, connection, queue, timer, retry, and callback has bounded
  ownership and shutdown.
- Selector reads remain local and immutable.
- Comments add non-obvious information and match current behavior.
- Safety, concurrency, lifecycle, security, and performance claims are backed
  by invariants or tests.
- Related `codex.md`, `alpha.md`, `protocol.md`, or `worklog.md` facts are
  updated.
- No commit or push is created without the maintainer's explicit instruction.
