# Verdandi Protocol Draft

## 1. Status and Authority

Status: **experimental implementation draft shipped with SDK `0.1.0`, targeting
the stable SDK `1.0.0` and protocol `1.0` contract**. The Registration Lua programs and initial Go and Rust
Register/Selector slices exist. Catalog Lua and the Go/Rust Publisher,
Subscriber, stable Entry, generic Load, and optional checkpoint slices also
exist; the remaining protocol subsystems
are not implemented.

This document defines behavioral and storage requirements that every SDK must
share. Implemented Registration fields, identifier alphabets, MessagePack
encoding, and Redis-backed default limits are exact Alpha contracts. Generic
Leader election is explicitly excluded. Examples for unimplemented supported
subsystems remain illustrative until their executable artifacts exist.

The canonical release contract will consist of:

- schemas and their compatibility rules;
- exact Redis field, scalar, key-segment, and hashing rules;
- stable string results and statuses;
- reviewed Redis Lua programs;
- byte-exact conformance vectors; and
- this protocol's normative state transitions.

Words such as **must**, **must not**, **should**, and **may** describe intended
requirements but do not constitute a stable compatibility promise before the
formal `1.0.0` contract is frozen.

## 2. Terminology

- **Zone:** an SDK-configured administrative and deployment isolation boundary
  inside one Redis deployment.
- **Type:** one application-defined Registration class discoverable through one
  leased Registry inside a Zone.
- **Node:** one running service process using a Verdandi SDK.
- **Registration ID:** one fresh UUID generated for that process start.
- **Publisher:** an authorized producer of Catalog KV and desired state.
- **Registration revision:** a positive per-Registration content version owned
  and validated by its SDK process, then atomically compared by Redis Lua. It advances only when mutable
  Selector-visible content changes; lease renewal retains the same revision.
- **Shared revision:** a strictly increasing Redis-owned mutation number within
  a Catalog, desired target, or ACK scope.
- **Registration:** one leased service record, identified by its per-start UUID
  and stored as a Redis Hash.
- **Registry:** the Zone/Type collection of live Registrations, represented by
  one membership Hash and one event channel with the same name.
- **Catalog:** one persistent revisioned raw Value, Array, or Map at a Part/ID
  Path, interpreted by an external SDK codec and held complete by Subscribers.
- **Desired document:** an opaque application snapshot plus Verdandi
  metadata.
- **ACK:** a Registration-owned acknowledgement of receipt, validation,
  activation, rejection, expiry, or drain.
- **Registration event:** one disposable Pub/Sub `register`, `update`, `renew`,
  or `unregister` message. A validated event normally updates the local view
  directly; an unresolved per-Registration revision gap invokes a bounded
  authoritative repair.
- **Zone configuration:** one SDK-initialized, Administrator-managed,
  non-expiring Redis Hash containing shared limits that every SDK in a Zone
  must interpret identically.

## 3. Identifier Requirements

Identifiers must have a canonical byte representation and a bounded length.
An SDK must reject non-canonical, empty, oversized, or invalid identifiers
before using them in a key, log, metric label, or allocation.

The application supplies `zone` through SDK configuration because all
participants in an administrative domain must share it. Its canonical form is
case-sensitive `[A-Za-z]{1,32}`. The SDK generates `uuid` as a fresh
128-bit value on every process start and encodes it as exactly 32 lowercase
hexadecimal characters `[0-9a-f]{32}` without separators.

Required identities:

- `zone` scopes administrative ownership and deployment isolation;
- `type` identifies one logical Registration class and Registry;
- `uuid` is a fresh UUID generated by the SDK for every process
  start;
- Registration `revision` orders one process's accepted content states;
- shared revisions order Catalog, desired-state, and ACK mutations.

User-provided display names must not be used directly as unescaped Redis key
segments. The accepted identifier contract uses case-sensitive
`[A-Za-z][A-Za-z0-9_.-]{0,63}` for Type and Catalog identifiers. The form
excludes `:`, Redis ACL glob characters, empty
segments, and Unicode normalization differences. A Catalog business key is
not a second identity in v1: the Catalog identifier names its one raw Value
directly.

## 4. Version Model

Every protocol-owned Redis data class identifies or inherits:

- Verdandi protocol major/minor version;
- content type for opaque application payloads; and
- optional producer SDK identity for diagnostics only.

The Go, Rust, C++, and C# SDK source/package version for the current Alpha is
`0.1.0`; the intended first stable protocol version remains `1.0`. These are
independent version domains. Before SDK `1.0.0`, the protocol identifier is an
experimental implementation marker rather than a public compatibility
guarantee, so distributed consumers must pin an exact `0.x` release and upgrade
all participants deliberately.
Package semantic version describes a released SDK API. Protocol major describes
the compatibility family; a different major is rejected. Protocol minor permits
only additive optional fields or new independent keys and cannot change an existing
field's meaning, type, owner, or validation.

Protocol `1.0` has no protocol capability metadata or negotiation. Every
defined behavior is mandatory. Registration fields describing what a
discovered service can do are separate application metadata named
`service_capabilities`. A future same-major minor must remain readable by older
same-major SDKs; any new mandatory behavior requires a new major.

Redis key names, existing Redis data types, and existing field meanings are
forward-compatible and do not change in place. Compatible evolution adds
optional fields or new keys. An unavoidable incompatible storage change uses
an explicitly new key family and migration rather than reinterpreting existing
keys.

No consumer may infer compatibility from a package version string alone.

## 5. Common Redis Field and Blob Rules

Ordinary coordination state uses protocol-defined Redis keys, data types, Hash
fields, scalar byte encodings, and Lua actions rather than one universal binary
envelope. Every owned field defines its name, type, required/optional status,
range, resource bound, mutation owner, and stable error behavior.

Registrations and complete Catalog Values are independent Redis Hashes. A
Registration has three stored field classes: Redis/Lua-managed Meta names begin with `@`,
immutable SDK-supplied Attr names begin with `.`, and mutable SDK-supplied Data
names are unprefixed. Data names may not begin with `&`, `@`, or `.`. Attr and
Data are fixed typed structures whose top-level fields are stored separately;
a nested structure remains one opaque bounded field value. A Data patch omits
unchanged fields and sets zero, false, empty, or encoded-null values explicitly.
There is no field-delete operation for a fixed Data structure. Catalog instead
has an external-codec raw Value: `@` fields are its four protocol metadata
leaves, `&` remains reserved, and all other fields are opaque application bytes
that Patch may set or delete.

Pub/Sub envelopes reserve `&` for message control, reuse `@` for Registration
Meta, reuse `.` for Attr, and leave Data unprefixed. The envelope is a
MessagePack array of alternating string keys and values. Encoders use one
canonical order, while decoders match keys rather than positions, reject odd
element counts and duplicate keys, and ignore unknown optional fields. Private
SDK-to-Lua requests use operation-specific fixed control-value positions,
followed only where needed by named Attr/Data field-value pairs. Lua replies use
flat named RESP arrays. Lua never parses JSON or application Attr/Data bytes.

The storage prefixes are not language member names. SDK users see ordinary
`Registration.Meta`, `Registration.Attr`, and `Registration.Data` members. Go
tags, Rust attributes, Python dataclass metadata, Node schemas, C++ descriptors,
or explicit codecs map them to canonical Redis fields. Automatic language-
specific reflection is not a cross-language wire contract.

An SDK reads and retains the known fields required by protocol `1.0` and
ignores unknown optional Hash fields. Correctly provisioned ACLs and protocol-owned Lua
enforce supported writes; deliberate raw mutation by a principal with raw write
permission is outside the protocol guarantee.

Records and manifests still carry enough bounded metadata to validate before
large allocation where applicable:

- message kind and protocol version;
- canonical target identity;
- Registration identity where applicable;
- revision where applicable;
- issue/sample time and validity/lease duration where applicable;
- declared encoded and decoded lengths;
- content/hash algorithm identifiers where applicable; and
- integrity metadata required by the message class.

SDKs validate Redis types, scalar byte encodings, integer conversions, declared
sizes, supported algorithms, and collection bounds before allocating or
indexing. Catalog field bytes and desired-state payload bytes are not
normalized by Verdandi.

Every shared Publisher-owned scope keeps its revision in Redis. Registration
revision is different: the owning SDK process retains, validates, and advances
it only for content changes, while Lua compares it with current Redis state and
stores it atomically. A fresh process receives a fresh UUID and begins at revision one.
Within one subscription generation, Selector state is ordered first by content
revision and then, for equal revisions, by Redis timestamp. A resolved primary
change starts a new Selector synchronization generation, while each live Node
publishes a complete `register` for its retained UUID, revision, immutable
attributes, TTL, and current content.

Time values use one explicitly defined epoch, unit, range, and overflow rule.
Lease expiry calculations use a monotonic local clock after authoritative data
is received; wall time is used only for absolute validity windows.

## 6. Illustrative Redis Key Ownership

The Zone configuration, Registration, Registry, Catalog, and product prefix are
accepted. Existing key meanings are forward-compatible. Other related key
shapes are drafts until the remaining identifier alphabets and escaping rules
are frozen:

```text
verdandi:config:<zone>

verdandi:registration:<zone>:<type>:<uuid>
verdandi:registry:<zone>:<type>
verdandi:ack:<zone>:<uuid>

verdandi:catalog:<zone>:@meta
verdandi:catalog:<zone>:@live
verdandi:catalog:<zone>:@deleted
verdandi:catalog:<zone>:@deleted_time
verdandi:catalog:<zone>:<part>:<id>
verdandi:catalog:<zone>:<part>:<id>:@field_revisions

verdandi:desired:<zone>:<target-token>:current
verdandi:desired:<zone>:<target-token>:manifest:<revision>
verdandi:desired:<zone>:<target-token>:chunk:<revision>:<index>
verdandi:desired:<zone>:<target-token>:wake
```

`verdandi:registry:<zone>:<type>` is both the Registry Hash key and its Pub/Sub
channel. Redis keys and Pub/Sub channels occupy independent namespaces, so the
shared text is unambiguous and prevents a second wake-key convention.
Each Catalog Path Hash key is likewise its complete-operation Pub/Sub channel.

Applications receive opaque protocol handles or typed identifiers and must not
construct these keys or issue Redis mutations. The SDK generates the per-start
UUID and owns all protocol keys. The final layout must permit ACL patterns
and all keys touched by one Lua operation must be compatible with the selected
deployment model.

### 6.1 Redis-backed Zone Configuration

Every Client bootstrap reads this non-expiring Hash. If any recognized field is
missing, bootstrap fills only that field with the common default through
`HSETNX`, then rereads and validates the complete recognized field set. This
makes concurrent first Clients safe without overwriting a value already placed
by an administrative backend:

```text
key: verdandi:config:<zone>

protocol                                         = v1
registration_attr_max_fields                     = positive decimal integer
registration_data_max_fields                     = positive decimal integer
registration_max_field_name_bytes                 = positive decimal integer
registration_attr_max_field_value_bytes           = positive decimal integer
registration_data_max_field_value_bytes           = positive decimal integer
registration_max_bytes                            = positive decimal integer
configuration_refresh_ms                          = positive decimal integer
```

| Field | Bootstrap default | Protocol ceiling |
| --- | ---: | ---: |
| Attr top-level fields | 16 | 128 |
| Data top-level fields | 32 | 128 |
| One application field name | 64 bytes | 64 bytes |
| One encoded Attr field value | 128 bytes | 16 KiB |
| One encoded Data field value | 128 bytes | 16 KiB |
| Complete Registration | 16 KiB | 64 KiB |
| Configuration refresh interval | 30,000 ms | 86,400,000 ms |

Attr and Data counts are independent; there is no combined 48-field or
protocol-wide service-count limit. `registration_max_bytes` counts the stored
byte length of every Hash field name plus every Hash field value, including
Registration Meta. Unknown optional configuration fields are ignored.

The key has no TTL. Ordinary Register/Selector APIs do not expose a way for an
application to mutate it, but an ACL-authorized administrative backend may
change the deployment policy after startup. Related changes use one Redis
multi-field `HSET`, which is the atomic configuration transition. A Client
retains one complete last-valid local snapshot. `configuration_refresh_ms` is
part of that snapshot, accepts 1,000 through 86,400,000 milliseconds, and
defaults to 30 seconds. Each Client waits the loaded value with plus or minus
ten percent jitter and exposes an immediate refresh operation; a newly adopted
value controls the next wait without restart. Registration and Selector
creation also performs an immediate refresh. A missing, malformed,
incompatible, or above-ceiling refresh is reported and does not replace the
last valid snapshot or its interval. Protocol `1.0` currently has no
configuration Pub/Sub channel or configuration revision, so automatic adoption
is bounded by each Client's configured polling interval rather than globally
simultaneous.

Lowering limits affects future Registration content mutations. The owning
Registration worker validates the complete projected record before advancing
revision or issuing Redis I/O; a record that no longer fits cannot change
content until it becomes compliant. Renew remains legal because it changes no
content. Selectors validate
stored and event state against protocol safety ceilings rather than the current
lower deployment policy, so a pre-existing valid Registration does not vanish
from discovery merely because an Administrator lowered an admission limit.
Raising limits takes effect after the next successful refresh, up to the fixed
protocol ceilings.

Local bootstrap data cannot come from this Hash because it is needed to reach
Redis. Standalone/Sentinel endpoints, Redis and Sentinel credentials, TLS,
connection deadlines, retry policy, and local concurrency/buffer budgets remain
local SDK configuration.

Only bootstrap fills absent defaults. If a backend later deletes a required
field, an already-running Client keeps its last valid snapshot and reports each
failed refresh; a newly opened Client restores the missing default. After Redis
data loss, retained local policy permits each surviving Registration worker to
recover its own desired state, while the next valid refresh or new Client
recreates the shared defaults.

## 7. Registration Worker and Record

### 7.1 Stored Shape

One running process owns one bounded Hash:

```text
key: verdandi:registration:<zone>:<type>:<uuid>

@uuid       = 32 lowercase hexadecimal characters
@revision   = positive safe integer
@timestamp  = Redis Unix time in milliseconds
@ttl        = positive integer milliseconds
@version    = positive safe integer
.<name>     = immutable typed Attr field bytes
<name>      = mutable typed Data field bytes
```

`@uuid`, `@revision`, `@timestamp`, `@ttl`, and `@version` are the complete
protocol `1.0` Registration Meta set. Attr and TTL are immutable for the UUID
lifetime; Version and Data are mutable Registration content. Registration
Version is application metadata and is not an election input. `@expire` is not
stored because the deadline is exactly
`@timestamp + @ttl`. `zone` and `type` are carried by the validated key and
SDK handle rather than duplicated in the Hash.

Attr and Data are fixed application structures. Their top-level fields are
expanded into the Hash to permit bounded partial Data updates. Attr is supplied
on the first full write and remains byte-identical for the UUID lifetime. Data
is mutable. An omitted Data field in an `update` means unchanged; an
explicit encoded zero or null clears its typed value. Nested changes replace
the complete top-level field value. A `register` removes obsolete unprefixed
Data fields before writing the complete current Data structure.

The Registry Hash is:

```text
key and channel: verdandi:registry:<zone>:<type>
field:           <uuid>
value:           <revision>
field expiry:    the same absolute deadline as the Registration key
```

The revision value is a content-synchronization hint and diagnostic. A `renew`
does not change it, but `HSETEX` rewrites the same value while refreshing field
expiry and can therefore repair a missing membership field. A Selector that
reuses same-revision cached content reads the current `@timestamp` through a
bounded pipelined `HMGET`, while a new or changed revision requires the complete
Registration.

### 7.2 SDK Ownership and Serialization

The SDK generates the UUID once at local Registration construction and keeps the
same UUID, immutable Attr, immutable TTL, desired Version and Data, and content
revision in one bounded process-memory desired-state cache, together with its
confirmation status, across Redis disconnects. The SDK does not write
Registration content, its UUID, or a replay log to local files, a local database,
or a WAL. A process restart discards the cache and generates a new UUID; the
previous Redis Registration expires by TTL.

After publication, every Registration owns one single-slot Fields merge
mailbox, one capacity-one wake signal, one long-lived synchronization worker,
and one renewal timer. The worker is the sole Redis writer for that UUID and
owns its desired/confirmed state. Registrations do not share a Client-level
mutation queue: a backlog, timeout, or recovery for one UUID cannot block an
unrelated UUID's worker. The Go and Rust `1.0` implementations default to eight
admitted result waiters per Registration and accept a configured range of
1..256. The bound does not create that many request or Data objects: one mailbox
retains only the latest pending Version and value for each changed field, while
a capacity-one signal merely wakes the worker. Caller cancellation bounds
waiting before admission; admitted work is reconciled to an actual outcome.
Changing TTL or Attr requires a new process UUID; a full recovery write merely
reconstructs their original values after the Redis key is absent while the same
process remains alive.

An application update is encoded and validated before its owned Fields enter
that UUID's mailbox. The SDK does not retain the application struct after
encoding. Later pending values for the same Version or Data field replace
earlier values; all Update waiters absorbed by one real write observe its one
result and revision. A same-batch Renew shares a successful effective Update's
lease refresh, but performs its own Redis Renew when the Update is a no-op or
fails. If the folded desired state equals confirmed state, the Update is a local
no-op and performs no Redis command. A transport-ambiguous result, Redis reconnect,
resolved-primary change, or missing key marks only that UUID for a complete
write; its worker never guesses that a partial mutation failed.

Registration initialization obtains the Client's current last-valid Zone
configuration and encodes the complete desired Meta/Attr/Data field map. Before
advancing the content revision or issuing Redis I/O, the Registration worker
validates the complete post-update map against all six active Registration limits. Byte
accounting is the sum of exact encoded field-name and value lengths. Because
Redis supplies `@timestamp`, the SDK reserves its field name plus the
16-decimal-digit safe-integer maximum; this is a safe upper bound for the value
that Lua can store. A failed check leaves the in-memory desired state, confirmed
state, and revision unchanged and returns a stable local capacity error.

Lua does not repeat protocol-version, kind, identifier, field-shape, immutable-
field, or capacity validation. The SDK keeps and validates the complete desired
record in bounded process memory before every Redis mutation. Lua retains only
atomic preconditions that require current Redis state and the derived deadline
needed by Redis expiry commands. A principal that bypasses the SDK while
holding raw script/write permission is outside the protocol guarantee. A
Selector validates fetched records against immutable protocol ceilings before
making them selectable; live deployment limits govern update admission, not
retroactive discovery.

A deterministic `missing` response consumed no content mutation, so recovery
reuses the current desired revision in a complete `register`. An ambiguous
partial result is reconciled by sending the complete desired state at its
proposed content revision; the full write is safe whether that revision was
already installed or not. Revision gaps are legal for `register`. A graceful
Close stops new writes, waits behind that UUID's already admitted requests, and
sends `unregister` only through the still-current healthy connection generation.
An ambiguous or disconnected Close never reconnects merely to delete and never
publishes another mutation for that UUID; natural TTL performs final cleanup.

Every successful Register, Update, and Renew reply must contain the exact
expected positive revision and a nonzero Redis timestamp. A mismatch or malformed
post-dispatch reply is `corrupt`, not confirmation. Like `ambiguous`, it retains
the latest desired state, marks that Registration uncertain/unhealthy, and makes
the next Update or Renew use a complete Register. This validation is performed
in every SDK; Lua remains the atomic mutation layer rather than the response
trust boundary.

The SDK API, Redis mutation kind, and Pub/Sub event kind use the same four
strings:

- `register` writes complete state for initial registration, recovery, or reset;
- `update` writes a Version and/or Data content change and advances revision;
- `renew` changes only Redis timestamp and lease expiry without advancing
  revision; and
- `unregister` removes the complete Registration and membership field.

A disconnected Close sends no delayed `unregister` and relies on TTL. There is
no `touch`, `batch`, `replace`, generic empty update, or `delete` Registration
wire kind.

The SDK invokes one operation-specific Registration Lua program for each of
these four kinds. The selected SHA is both protocol-v1 layout and operation
dispatch. Fixed request controls therefore carry values only; neither
`&protocol`, `&kind`, nor fixed Meta field names are repeated. Dynamic Attr and
Data retain names in their payload tail. Replies and Pub/Sub events remain
self-describing alternating key/value arrays. An incompatible future request
layout uses a new script/SHA rather than reinterpreting v1 positions.

### 7.3 Register, Update, and Renew Mutations

The exact Redis arguments for an initial or recovery `register` are:

```text
ARGV[1]  = "7f4a0d92c8154e7f8a31b922d314ae60"  # UUID
ARGV[2]  = 42                                  # content revision
ARGV[3]  = 30000                               # TTL milliseconds
ARGV[4]  = 12                                  # Registration version
ARGV[5]  = ".build"                            # Attr name
ARGV[6]  = <binary>                            # Attr value
ARGV[7]  = ".region"
ARGV[8]  = <binary>
ARGV[9]  = "address"                           # Data name
ARGV[10] = <binary>                            # Data value
ARGV[11] = "load"
ARGV[12] = <binary>
```

The SDK has already validated the complete record and guarantees that one
revision identifies one content state. It rejects an incoming revision below
the stored revision. An equal or greater revision replaces the complete
SDK-validated Version/Attr/Data state, obtains a new Redis timestamp, refreshes
the lease, and publishes a complete `register` event. The supported SDK retains
the UUID, TTL, Attr, current Version, and desired Data across reconnect recovery.
None of these Registration operations mutates another protocol data class.

A partial Data `update` is:

```text
ARGV[1] = "7f4a0d92c8154e7f8a31b922d314ae60"  # UUID
ARGV[2] = 43                                  # next content revision
ARGV[3] = "13"                                # changed Version or empty
ARGV[4] = "load"                              # changed Data name
ARGV[5] = <binary>                            # changed Data value
```

The SDK requires a Version change and/or at least one changed Data field and
emits the next revision. An empty Version slot means unchanged. Lua compares
that revision with current Redis state: equal is an idempotent acknowledgement,
current plus one installs the patch, lower is stale, and a gap is a transition
error. Lua does not compare equal-revision payload bytes because the SDK owns
the revision-to-content invariant.

A lease renewal is a distinct mutation:

```text
ARGV[1] = "7f4a0d92c8154e7f8a31b922d314ae60"  # UUID
ARGV[2] = 43                                  # unchanged revision
```

The SDK supplies only UUID and the current revision. Lua requires that revision
to equal current Redis state. Retrying it is another valid proof of current
liveness and may therefore obtain a newer timestamp and extend the fixed lease
again.

After SDK validation, the one Lua execution:

1. obtains Redis Unix milliseconds from `TIME` and, for an existing record,
   selects `timestamp = max(redis_time, stored_timestamp)` so an equal-revision
   renewal cannot regress the lease;
2. loads the immutable stored TTL when Update or Renew must refresh expiry;
3. checks `deadline = timestamp + ttl` for range, overflow, and Redis 8's
   Hash-field absolute-expiry ceiling `2^46-1` milliseconds;
4. applies the complete, partial, or timestamp-only Hash mutation;
5. stores `@timestamp`, and stores `@revision`, `@ttl`, `@version`, Attr, or Data
   only when required by that kind;
6. applies `PEXPIREAT` to the Registration key;
7. stores the Registry field `<uuid> = <revision>` and its identical absolute
   field deadline in one `HSETEX ... PXAT` command for all three live operations
   (Renew rewrites the same value to repair absence); and
8. publishes the corresponding `register`, `update`, or `renew` event.

A confirmed real Update refreshes the Redis lease in that same Lua execution and
resets the worker's next automatic Renew deadline. A confirmed Renew likewise
resets it. A rejected or exact local no-op Update cannot prove Redis liveness and
therefore must not postpone an already-due Renew; the worker prioritizes admitted
work but follows it with Renew when the timer is still due.

No accepted mutation scans another Registration or increments a Registry-wide
counter. A full `register` reads only its own current revision/timestamp, then
deletes and replaces a present valid Hash so obsolete fields cannot survive; if
both known fields are absent it installs directly without an empty-key `DEL`. A
new-revision `update`, `renew`, and `unregister` never issue `HGETALL`. Lua
treats Attr/Data values as opaque binary strings.

Successful RESP replies are alternating key/value arrays:

```text
["&result", "ok", "@revision", 42, "@timestamp", 1787371200123]
```

An idempotent content-update retry returns the installed timestamp in the same
shape. An accepted `register` or `renew` returns its newly selected timestamp.
Errors use readable strings and add only relevant context:

```text
["&result", "error", "&status", "missing"]
["&result", "error", "&status", "stale", "@revision", 45]
["&result", "error", "&status", "contract", "&field", "@revision"]
["&result", "error", "&status", "invalid", "&field", "@version"]
["&result", "error", "&status", "immutable", "&field", ".build"]
["&result", "error", "&status", "invalid", "&field", "@ttl"]
["&result", "error", "&status", "corrupt"]
```

### 7.4 Unregister Mutation

A graceful `unregister` command contains only the positional channel-local
identity:

```text
ARGV[1] = "7f4a0d92c8154e7f8a31b922d314ae60"  # UUID
```

The Registration worker has already drained that UUID's admitted content and
renewal mutations.
The SDK sends this command only on its still-current healthy connection and
treats it as terminal; it cannot later recover, renew, or reuse that process
UUID. These lifecycle rules make a second server-side operation sequence
unnecessary. Lua atomically deletes the complete Registration Hash, removes the
UUID field from the Registry Hash, and publishes one `unregister` event. A
missing Hash is already the requested final state: Lua removes residual
membership, returns success, and publishes nothing. Redis stores no tombstone or
delete history.

### 7.5 Registration Event Contract

Pub/Sub carries MessagePack arrays of alternating key/value items. Control
keys come first, then Meta, Attr, and Data; Attr and Data fields use canonical
bytewise field-name order. Protocol `v1` envelopes are flat: declared and
unknown optional values may be any non-extension MessagePack scalar: nil,
boolean, integer, float, string, or binary. Decoders reject nested arrays or
maps, extension values, excessive declared
pair counts, and trailing bytes before expanding the envelope. The decoded
`register` event carries complete state:

```text
[
  "&protocol",  "v1",
  "&kind",      "register",
  "@uuid",      "7f4a0d92c8154e7f8a31b922d314ae60",
  "@revision",  42,
  "@timestamp", 1787371200123,
  "@ttl",       30000,
  "@version",   12,
  ".build",     <binary>,
  ".region",    <binary>,
  "address",    <binary>,
  "load",       <binary>
]
```

An `update` event carries the identity, new content revision, Redis timestamp,
and only the changed content fields:

```text
[
  "&protocol",  "v1",
  "&kind",      "update",
  "@uuid",      "7f4a0d92c8154e7f8a31b922d314ae60",
  "@revision",  42,
  "@timestamp", 1787371200123,
  "load",       <binary>
]
```

An `update` cannot be empty. `@version` is present only when changed; Data
contains only changed top-level fields. Attr and `@ttl` appear only in
`register`.

The decoded `renew` event is:

```text
[
  "&protocol",  "v1",
  "&kind",      "renew",
  "@uuid",      "7f4a0d92c8154e7f8a31b922d314ae60",
  "@revision",  42,
  "@timestamp", 1787371201123
]
```

It contains no Attr, Data, `@ttl`, or `@version`. The repeated revision states
which cached content the renewed timestamp belongs to.

The decoded `unregister` event contains only the channel-local identity needed
to remove the terminal UUID:

```text
[
  "&protocol", "v1",
  "&kind",     "unregister",
  "@uuid",     "7f4a0d92c8154e7f8a31b922d314ae60"
]
```

These are the only four Registration event kinds. An explicit `unregister` is
terminal for that process UUID; the SDK must never publish a later event for
it. Redis TTL expiry emits no Verdandi event.

## 8. Registration Lease and RedisClock

Redis key TTL and Registry field TTL are authoritative for Redis-side liveness.
Selectors maintain one connection-generation RedisClock so normal Registration
events and reads do not issue `PTTL` or `HPTTL`.

A RedisClock calibration sends `TIME` while sampling the local monotonic clock
before and after the command. It derives a conservative upper estimate of Redis
time from the returned Unix time, measured round-trip interval, monotonic
elapsed time, and a configured uncertainty margin. It calibrates on every new
primary connection and periodically while that connection remains current. A
new connection generation never reuses the previous generation's calibration.

For each Registration:

```text
redis_deadline = timestamp + ttl
expired        = RedisClock.Upper() >= redis_deadline
```

`redis_deadline` must be at most `70,368,744,177,663` (`2^46-1`), the Redis 8
absolute-millisecond ceiling for Hash-field expiration. SDKs reject values that
are already impossible before I/O; Lua repeats the final check after obtaining
the authoritative Redis timestamp. The Registration key could represent a
larger key expiry, but its paired Registry field cannot, so the stricter shared
deadline governs both.

Using the upper estimate can expire a local record early but must not keep it
after Redis may consider it expired. A delayed Pub/Sub event carries its
original Redis timestamp; if its deadline is already past when decoded, the
Selector never admits it. Local wall-clock movement does not extend a deadline.

`@expire` is neither stored nor transmitted. `PTTL` and `HPTTL` remain bounded
diagnostic and corruption-recovery tools, not the normal synchronization path.
Deployments must keep Redis hosts under normal clock synchronization; the SDK
cannot mask an arbitrary forward or backward server clock jump without
conservatively expiring state.

## 9. Registry and Selector Driver

### 9.1 Membership and Event Ordering

One Registry Hash contains one independently expiring UUID field per live
Registration. Selectors enumerate it through bounded `HSCAN` pages and fetch
the corresponding Registration Hashes with bounded pipelining or concurrency.
`HSCAN` may return duplicates and may include or omit fields that change during
an iteration; the SDK deduplicates UUIDs and reconciles concurrent changes from
the already-live subscription.

Redis Pub/Sub preserves publication order on one subscribed connection but is
at-most-once and non-durable. Every Lua mutation changes record, membership,
expiry, and event atomically. There is no Registry-wide revision key, Stream,
journal, barrier mutation, or expiry index.

### 9.2 Initial Synchronization

A Selector owns one persistent listener/state-machine task. The listener is the
only Pub/Sub receiver and the only owner of mutable live state. It may start one
temporary task for either a full snapshot or targeted repair, never one of each;
therefore a Selector owns one task in steady state and at most two while
synchronizing. The temporary task performs bounded command reads and requests
the same-generation PING fence, then returns one candidate state. The listener
continues coalescing Pub/Sub input and alone installs that result. Close cancels
and joins the optional temporary task before the listener terminates.

A Selector synchronization generation is driven as follows:

1. Resolve the current Redis primary and open independent bounded command and
   subscription connections.
2. Subscribe to `verdandi:registry:<zone>:<type>` and wait for the exact
   subscription acknowledgement. Only then create the generation and begin
   buffering decoded events.
3. Calibrate the generation's RedisClock.
4. Walk the Registry Hash from cursor zero back to zero. Deduplicate UUIDs and
   retain each membership content-revision hint. For a matching active or
   retained local revision, pipeline only `@revision` and `@timestamp`; for a
   new or changed revision, fetch the complete Registration. Bound every page,
   pipeline, reply, and candidate byte count.
5. Validate every Hash type, UUID, Meta scalar, field class, Attr/Data schema,
   revision, resource bound, and derived deadline. Missing or expired records
   are not admitted.
6. After the final scan and fetch reply, issue `PING <nonce>` on the same
   subscription connection and continue buffering until the matching ordered
   `PONG <nonce>` is received.
7. Reconcile the buffered per-UUID `register`, `update`, `renew`, and
   `unregister` events with the fetched candidates. Resolve any remaining
   per-UUID gap through the bounded repair procedure below.
8. Recheck the connection generation and RedisClock, remove candidates whose
   deadlines have passed, and atomically publish one immutable local view.
9. Continue applying live events for the same generation.

The subscription acknowledgement closes the read-before-subscribe race. The
ordered PONG is not a fifth Verdandi event kind: it is Redis connection control.
Because it is received on the same subscribed socket after the scan completes,
all mutation messages Redis queued before that PONG have entered the Selector
buffer. Mutations processed later arrive after the PONG and follow the normal
live path.

### 9.3 Event Application

For `register`, the complete event installs an absent UUID or replaces an equal
or newer content revision. A lower revision is ignored within the same
subscription generation. Equal revision refreshes timestamp and lease while
retaining the invariant that the complete content bytes are identical.

For `update`:

```text
incoming revision <= local revision
    ignore as duplicate or delayed

incoming revision == local revision + 1
    apply the partial Data fields and timestamp

otherwise
    mark this UUID for authoritative repair
```

For `renew`:

```text
incoming revision < local revision
    ignore as delayed

incoming revision == local revision
    retain content and set timestamp = max(local, incoming)

incoming revision > local revision
    a content update is missing; mark this UUID for repair
```

A live deadline derived from a matching `update` or `renew` may reactivate
retained content.
An `unregister` from the current subscription generation immediately removes
both active and retained data for that terminal UUID. It needs no revision in
the event because the SDK may never reuse an explicitly unregistered process
UUID and old-generation buffers are discarded in full.

A `register` is self-contained and may repair any earlier gap. An `update`
never creates a Registration without a matching local base, while `renew`
never changes content.
Unknown optional keys are ignored, but malformed MessagePack, duplicate keys,
an unknown mandatory protocol major, an invalid field class, or an impossible
revision transition fails the event.

Application field names are non-empty valid UTF-8 byte sequences. Their byte
representation is significant: SDKs do not apply Unicode normalization. This
keeps Go, Rust, Node.js, Python, C++, and Redis field identity consistent while
allowing non-ASCII struct-field mappings.

### 9.4 Bounded Per-Registration Pending State

While synchronizing or while application publication is coalesced, the
Selector retains at most one pending logical change per UUID:

- contiguous `update` events merge by top-level field with last value winning
  and retain the latest revision/timestamp;
- a `renew` for the same revision raises the queued timestamp without changing
  content;
- a `register` replaces the queued change with complete state;
- an `unregister` replaces the queued change and purges retained data; and
- a non-contiguous sequence marks the UUID for repair instead of accumulating
  an unbounded list.

Total pending entries and bytes remain configured bounds. One entry per UUID
prevents update rate from multiplying queue memory, but it does not create a
fixed Registry population limit.

### 9.5 Targeted Repair

On a live per-UUID gap, the subscription remains active while the Selector
fetches that complete Registration or its absence, then sends another
`PING <nonce>` on the same subscription connection. Events for the UUID remain
coalesced until the matching PONG. The fetched state plus all preceding queued
events produces either a current Registration or confirmed absence. Targeted
repair uses the same optional synchronization-task slot and does not increment
the Selector generation. Only a successful full synchronization after opening
a subscription generation increments it.

Starting targeted repair immediately marks the published view unavailable.
Private active/retained state and incoming coalesced events remain available to
the owner loop for recovery, but no public selection or snapshot operation may
consume that half-synchronized state. The view becomes usable again only after
the repair result and same-connection PING fence have been accepted atomically.

A subscription disconnect, hidden reconnect, changed primary, PONG timeout,
buffer overflow, invalid clock generation, or repeated non-converging repair
abandons the whole candidate and restarts acknowledged synchronization. A
driver that silently reconnects Pub/Sub without exposing a new generation is
non-conformant.

### 9.6 Local View and Expiry

The Selector owner loop maintains mutable private records, one indexed deadline
per UUID, and a bounded change set. It publishes immutable application views in
coalesced batches rather than copying the complete Registry for every renewal.
Selection performs no Redis command. A `renew` updates only private timestamp
and deadline state; it does not rebuild an unchanged payload or force a public
view copy. Data, Registration Version, addition, explicit unregister, or
local-expiry changes become visible in the next bounded publication cycle.

Every raw and typed public active, retained, policy, and complete-snapshot API
returns explicit `unavailable` while the view is not synchronized. This applies
to Snapshot, Find, FindRetained, One, and Any; a stale boolean marker is not a
substitute for the error. `One` and `Any` use the initial simple O(N) policy
scan. A detached complete Snapshot necessarily copies O(N) records and is
documented as a heavy operation accepted by its caller.

During a network outage private last-known state may retain only records whose
existing RedisClock-derived deadlines have not passed, but the public view is
unavailable until a new synchronization fence succeeds. Once TTL expiry or a
fenced membership scan confirms non-explicit absence, the record leaves the
private active set immediately but its payload may move to a configured time-
and byte-bounded recovery cache. Retained data never extends a lease or
participates in selection; it only permits cheap reactivation by a valid event
or reconnect.
The retained deadline is exactly `@timestamp + 2*@ttl`, which supplies one
additional TTL after the active deadline. An explicit `unregister` purges it
immediately. Natural Redis expiry has no event, so the indexed local deadline
remains required. If Pub/Sub loss hides an Unregister, the later authoritative
absence is indistinguishable from TTL expiry and may enter recovery cache; it
remains non-selectable and is still purged by its deadline or byte budget.
Initial SDK defaults use an independent 64-MiB retained budget, zero disables
it, 1 GiB is the accepted maximum, and pressure evicts the earliest deadline.

### 9.7 No Registry Count Limit

The protocol defines no maximum number of Nodes, Registrations, or Registry
records. Every Lua mutation touches one bounded Registration and one membership
field. Page entries, page bytes, fetch concurrency, pending changes,
synchronization duration, immutable-view bytes, and subscriber output are
independently configurable and bounded. A deployment that cannot materialize
its configured view reports capacity without turning that local resource limit
into a protocol-wide record-count ceiling.

### 9.8 Qualification Status and Remaining Risks

The initial Go and Rust adapters have passed exact payload-bearing Pub/Sub
PING/PONG ordering, bounded one-pending-logical-change-per-UUID coalescing,
retained expiry/reactivation/purge, live cross-language MessagePack
interoperability, five-minute sustained update and renewal phases with eight
Selectors, 5,000-record pagination, and a real three-node Redis
8.8/three-Sentinel promotion and recovery matrix. The remaining qualification
risks are:

- MessagePack key/value event encoding cost versus a custom fixed binary frame;
- Redis Lua latency for full Attr comparison and full Data replacement at the
  maximum Registration size;
- Redis Pub/Sub output-buffer and network cost above the qualified eight-way
  subscriber fan-out;
- RedisClock behavior under long delayed responses and host clock steps;
- sustained high fan-in while the Rust driver's bounded ingress broadcast
  buffer feeds the per-UUID coalescer; and
- multi-hour churn and repeated failover storms.

The original Registration Sentinel evidence qualifies only the implemented
Register/Selector slice; later TLS and Catalog evidence is recorded separately.
Generic Leader election is outside this protocol.
Any future adapter that cannot expose PING/PONG in receive order requires a
separate synchronization control channel or a third barrier message; it must
not use an unfenced scan.

## 10. Observed Load Updates

Observed load is an ordinary fixed Data field or bounded group of top-level
Data fields. The Node coalesces connection-level changes into its desired Data
and publishes them through the same serialized `update`; there is
no separate load command or index.

Selectors receive changed load bytes inline and therefore perform no routine
Redis pull per update. Consumers ignore stale revisions and may maintain a
bounded local pending-reservation overlay until a later Registration update
reconciles it. SDK configuration bounds publication cadence, thresholds,
coalescing, pending reservations, and immutable-view publication cadence.

## 11. Catalog Value Synchronization

### 11.1 Path and raw shapes

One Catalog path is exactly:

```text
verdandi:catalog:<zone>:<part>:<id>
```

`part` matches `[A-Za-z0-9_.-]{1,64}`; `id` uses the same alphabet with 1..128
bytes. The key stores one Redis Hash and is also its Pub/Sub channel.

The Hash has exactly one top-level shape:

- Value: one application field named `value`;
- Array: a contiguous sequence of canonical decimal fields `0..n-1`; or
- Map: non-empty UTF-8 application field names that do not begin with `@`.

Field values are opaque binary strings and may be empty. Verdandi does not
define a Catalog Data schema or nested type system. Application-owned codecs
project the complete raw fields into any external type.

One complete encoded representation counts every application field-name byte
plus field-value byte. It defaults to and may not exceed 524,288 bytes.
Segmented Replace, out-of-line references, Array holes, and implicit nested
differencing are not protocol operations.

### 11.2 Replace, Patch, and Delete

An authorized Publisher exposes exactly three mutations:

- Replace atomically writes one complete Value, Array, or Map and is
  last-write-wins;
- Patch atomically adds or overwrites Map fields, or overwrites existing Array
  indices, only when `base_revision` equals the exact current path revision;
- Delete atomically removes the complete Hash and creates a fresh tombstone,
  including when the path is absent or already deleted.

Patch must contain at least one field. It cannot operate on Value, delete a
field, append/truncate an Array, create an Array hole, or change shape. Those
changes require Replace.

The SDK validates and encodes values before one bounded Lua mutation. Replace
and Delete need no external lock because Redis executes each script atomically.
For Patch, the SDK reads the current header and affected fields to project the
final byte size, then Lua rechecks the exact `base_revision` and all projected
invariants before its first write. If another same-Path mutation wins between
the read and script, Patch returns `stale` without changing state.

Replace and Delete do not compare an application revision. Patch is strict:
the mutation validates the same exact `base_revision` used for projection. A
stale base fails without state change. A transport failure
after a mutation was sent is `ambiguous` because Redis may already have
committed it; a controller repairs its current revision before another Patch.

### 11.3 Revisions and Redis state

The Zone owns one Redis-primary execution-order revision in
`1..=9007199254740991` (`2^53-1`). Zero means no revision. Every accepted
Replace, Patch, and Delete allocates exactly one new revision. Control integers
are canonical unsigned decimal strings; the same revisions are exact Redis
sorted-set scores.

The Zone-level keys are:

```text
verdandi:catalog:<zone>:@meta
verdandi:catalog:<zone>:@live
verdandi:catalog:<zone>:@deleted
verdandi:catalog:<zone>:@deleted_time
```

`@meta` is a Hash containing `@revision` and `@floor_revision`. `@live`
is a ZSET from `<part>:<id>` to its current live revision. `@deleted` maps
retained deleted members to their delete revisions. `@deleted_time` maps the
same retained members to Redis TIME in milliseconds.

A live path Hash reserves exactly:

```text
@revision
@replace_revision
@kind
@encoded_bytes
```

The companion
`verdandi:catalog:<zone>:<part>:<id>:@field_revisions` ZSET maps every
application field name to the revision that last changed it.
`@replace_revision` is the revision of the most recent complete Replace.
Deleted paths have neither data Hash nor field-revision ZSET.

Tombstones are bounded by age and count. The current fixed policy retains them
while both 24 hours and 1,000,000 members permit it, pruning at most 256 on one
Delete. Expired records are removed first, then only the actual count excess.
`@floor_revision` advances monotonically to the highest delete revision
actually evicted; it does not advance merely because Delete occurred.

### 11.4 Atomic notifications

Replace, Patch, and Delete Lua scripts commit the authoritative state, indexes,
revision, and one Pub/Sub notification atomically. Lua derives the MessagePack
notification from the exact operation it commits.

Every notification begins with protocol `v1`, operation, and
`<part>:<id>`. Replace contains accepted revision, shape, final encoded bytes,
and all fields. Patch contains exact base revision, accepted revision, shape,
final encoded bytes, and every set field. Delete contains the accepted delete
revision.

Pub/Sub delivery is at-most-once and therefore not an authoritative log. A
notification is a complete fast-path operation. Loss, malformed data, a Patch
whose base is not locally current, or reconnect invokes authoritative Redis
repair.

### 11.5 Subscriber alignment and repair

One Subscriber covers any non-empty union of the complete Zone, Parts, and
exact Paths. Redundant exact Paths are removed when broader coverage contains
them. It owns one dedicated persistent Pub/Sub connection/listener for all
exact channels and patterns and at most one temporary authoritative
synchronization/repair task. Pending scope and Path work coalesces into that
temporary slot, which exits when idle. It does not create one thread or
connection per subscription.

Initial and reconnect synchronization must:

1. subscribe and receive all subscription acknowledgements;
2. read Zone revision and floor;
3. use full live/deleted ZSET scans when the local cursor is zero, ahead of
   Redis, or below floor; otherwise read members in `(cursor, revision]`;
4. read every selected changed path through the atomic Read script;
5. send PING on the subscribed connection and wait for its ordered PONG;
6. reread Zone metadata and repeat if the floor overtook the captured revision;
7. publish complete aligned Entries and then persist the scope cursor.

Read returns absent, deleted, unchanged, a complete replacement, or only fields
whose revision exceeds the caller's local revision. It returns a delta only
when the local revision is at or after `@replace_revision`; otherwise it
returns the complete Hash.

A valid Replace or Delete may update an Entry directly. A Patch may update it
only when the Entry revision exactly equals the event's base. Any mismatch
marks that path Synchronizing and invokes Read. A reconnect, notification parse
failure, or new subscription acknowledgement requests scope repair. Repair
concurrency, Redis pages, retries, diagnostics, and decoded payload sizes are
bounded.

A stable Entry survives replacement, deletion, and recreation. Its state is
Present, Absent, Deleted, Synchronizing, Unavailable, or Closed. During
Synchronizing or Unavailable it may retain the last complete value but must
label it non-synchronized. A typed Load is a local projection and performs no
Redis or disk I/O.

### 11.6 Optional local checkpoint

A Subscriber always owns its complete covered working set in memory. An
optional local KV database is a restart accelerator only: Go uses bbolt and Rust
uses redb. Files need not be portable between SDK languages.

Checkpoint entries and the normalized-scope cursor advance monotonically.
State for a revision is persisted before the cursor can advance past it.
Concurrent same-scope Subscribers cannot replace a newer stored entry or cursor
with an older one. On the first read/write/corruption error, persistence is
disabled for that Client generation and reported asynchronously; in-memory
Redis synchronization continues.

Redis is always authoritative. Local state is never written back to Redis and
does not add a memory-to-disk-to-network consistency tier. A cursor below
`@floor_revision`, ahead of Redis, corrupt, or incompatible triggers full
authoritative alignment.

## 12. Excluded Leader Election

Protocol `1.0` defines no generic Campaign readiness, Leader election,
distributed lock, ownership term, election key, or election Lua action.
Registration `@version` remains application-defined metadata that Verdandi
stores and synchronizes without interpreting it as an election priority.

Redis Sentinel primary discovery and failover remain supported transport
behavior. They recover the Redis backend and do not expose an application
Leader API or exclusivity guarantee. Applications that require exclusive
leadership must use a dedicated external coordination system.

## 13. Desired Configuration

Desired configuration is an opaque complete payload wrapped in a validated
Verdandi envelope. It uses the same chunk/manifest/current-pointer publication
pattern defined for immutable desired documents.

Required envelope concepts:

```text
protocol + envelope schema version
target scope and identity
revision
issued_at + not_before + expires_at
desired lifecycle state
content type + application schema version
encoding/compression identifiers
encoded + uncompressed lengths
content hash
opaque payload bytes
```

Zone is implicit in the key scope. A target is exactly one of
`partition(partition_id)`, `service(partition_id, service_id)`, or
`registration(registration_id)`. Multiple authorized Publishers use Redis-
revision last-write-wins: each publication reserves a revision, and the
highest successfully installed current revision remains current.

The exact field and chunk representation must be test-vector-backed. SDKs
must reject decompression bombs, unsupported codecs, length mismatches, wrong
targets, validity failures, rollback on an unchanged Redis connection, and
invalid hashes before application
activation. Write permission comes from Redis authentication and ACLs rather
than an end-to-end signature.

The application callback returns a stable accepted/rejected result and must
not expose partially activated state. Verdandi does not understand the opaque
payload or turn a Bifrost contract into a Verdandi dependency.

## 14. Acknowledgement

An acknowledgement contains:

- Registration UUID;
- acknowledged message kind;
- desired target and revision;
- one of the stable ACK states;
- stable error code;
- bounded sanitized diagnostic;
- activation/result time where applicable;
- Registration-local ACK revision; and
- ACK lease/TTL.

The owning Registration atomically replaces its ACK. One Registration cannot
acknowledge for another UUID. A Publisher may treat only an authoritative ACK
for the expected target, Registration UUID, and revision as
convergence.

ACK states are `received(1)`, `validated(2)`, `active(3)`, `rejected(4)`,
`expired(5)`, `draining(6)`, and `drained(7)`. The generated transition table
permits idempotent self-transitions, `received -> validated`, `validated ->
active`, `received|validated -> rejected|expired`, `active ->
expired|draining`, and `draining -> drained|expired`. A newer desired revision
starts a separate state machine; every other transition returns
`invalid_transition`.

ACK revision starts at 1 and advances only when the record changes. Identical
same-state publication is idempotent; conflicting same-revision bytes fail.

## 15. Commands

Command delivery is deferred from SDK `1.0.0`. A future Command is a one-time
imperative action that cannot be expressed as desired state, and its design
must remain durable and bounded. A future entry would include:

- unique command ID and idempotency key;
- target scope and Registration policy;
- target revision;
- issue, not-before, and expiry time;
- command type and bounded opaque payload;
- content hash; and
- retention metadata.

Pub/Sub only wakes the reader. The Node reads durable entries, validates them,
checks expiry and duplicate state, executes an idempotent handler, and writes a
result ACK. Ambiguous execution is reconciled through idempotency state; the
protocol does not claim exactly once.

Retention is acknowledgement-aware and capped by count, bytes, and age. When
capacity is reached, publication fails explicitly rather than growing without
bound or silently discarding unacknowledged work.

## 16. Pub/Sub Mutation Events

Pub/Sub events are bounded, non-secret, non-durable mutation messages.
Registration subscribers normally apply a valid per-UUID event directly.
Catalog notifications carry a complete Replace, Patch, or Delete operation,
but remain disposable and repair from authoritative Hash/ZSET state as
described in Section 11. Events may contain:

- message kind;
- target identity;
- target revision or Registration UUID/revision; and
- a protocol version sufficient to reject incompatible notifications.

Registration `register` events carry complete state, `update` carries a content
patch, `renew` carries the unchanged revision plus Redis timestamp, and
`unregister` carries only UUID. Events must not contain complete desired
configuration, credentials, private endpoints, or arbitrary diagnostics.
Registration `register`, `update`, and `renew` events
carry Redis timestamp, so a Selector with the immutable cached TTL and current
RedisClock may refresh the exact local deadline without another Redis read.

Malformed, duplicate, stale, future-incompatible, and out-of-order events are
bounded to parse and cause either ignore or authoritative repair according to
the frozen state machine.

## 17. Atomic Operations

Lua scripts should remain small, deterministic, and bounded by explicit input
sizes. The implemented Registration actions are four operation-specific
programs generated deterministically from reviewed shared fragments. One
logical mutation selects and executes exactly one of those programs. Candidate
operations include:

- register, update, renew, or unregister one UUID Registration with its Registry
  membership field, matching expiry where applicable, and mutation event;
- replace one Registration acknowledgement with UUID and ACK-revision fencing;
- Replace one complete Catalog shape, apply one exact-base Patch, or Delete one
  complete path while updating global/field revisions, indexes, and Pub/Sub;
- atomically Read one Catalog path as absent, deleted, unchanged, complete, or
  an exact newer-field delta;
- advance the desired current pointer and target revision atomically.

Scripts must not scan the full Zone or every registered Node. Scripts
return stable string results and statuses rather than numeric enums or
library-specific exception text. Script reload after `NOSCRIPT` is part of
normal recovery and must be safe to repeat.

## 19. Redis Topology Rules

Alpha requires Redis Open Source 8.0.0 or later in a qualified Redis 8 line, or
a service proven compatible by the same integration matrix. Registry membership
depends on Hash-field expiration, including `HSETEX`, `HPEXPIREAT`, and
`HPTTL`; Registration writes use `HSETEX PXAT`, while the latter commands remain
compatibility/diagnostic paths.

### 19.1 Standalone

Use the configured primary endpoint. A reconnect targets the same endpoint
subject to bounded connection-recovery backoff. Dispatched commands are not
automatically replayed.

### 19.2 Sentinel

Query a bounded set of Sentinel endpoints for one configured master name.
Redis and Sentinel credentials, TLS identity, connection pools, deadlines, and
diagnostics are separate. A resolved Redis address is validated before use.

After Redis failure, resolve again. Do not use a remembered old primary merely
because all Sentinels are temporarily unavailable. Replica reads do not decide
Registry, Catalog, desired-state, lease, or ACK convergence.

### 19.3 Cluster

Redis Cluster is unsupported and has no scheduled support horizon. No SDK may
silently accept Cluster configuration or imply that key-slot distribution
preserves the required atomic behavior.

## 20. Reconnect and Recovery

Each recovery generation performs:

1. topology resolution;
2. authenticated command connection;
3. authenticated dedicated subscription connection when the recovered data
   class uses Pub/Sub;
4. Redis-backed Zone configuration refresh, validation, and last-valid snapshot
   publication;
5. script readiness as needed;
6. subscription and acknowledgement when required;
7. authoritative document load, Registry subscribe/scan/PING synchronization,
   or Catalog live/deleted ZSET plus atomic per-path Read alignment as appropriate;
8. atomic local publication;
9. republish of owned state if absent or behind; and
10. transition to `Ready`.

Old callbacks, notifications, futures, and Redis responses carry a local
generation token and cannot mutate current state after a newer recovery begins.

Connection-recovery concurrency, backoff, jitter, queued work, and diagnostics
are bounded. These bounds do not authorize replay of a command whose result may
be ambiguous. Shutdown cancels recovery and joins every owned task.

## 21. Security Rules

- Redis and Sentinel should be privately reachable and use TLS when traffic
  crosses host boundaries.
- ACLs are provisioned by role and Zone, not per Registration UUID.
  Initial roles are Node, Publisher, Selector, Catalog Subscriber, and
  Administrator; one credential may combine explicitly granted roles. Redis
  and Sentinel authentication are not reused implicitly.
- Redis authentication and ACLs are the write-permission boundary for
  Zone configuration, Registration, Registry, Catalog, desired state,
  and ACK data.
- Protocol-owned SDK/Lua actions preserve supported multi-key invariants. A
  principal granted raw write access can bypass them and is outside Verdandi's
  guarantee.
- Revision and reconnect rules fail closed. Registration state and operational
  configuration are not recovered from local disk. An explicitly enabled
  Catalog checkpoint is disposable acceleration only and never authority.
- Secrets never appear in keys, wake signals, errors, logs, or test fixtures
  committed to the repository.

## 22. Resource Limits

The final schema and SDK configuration must define units, legal ranges, and
safe defaults for all limits. Shared Registration record limits live in the
Redis-backed Zone configuration; bootstrap connectivity and local operational
budgets remain local SDK configuration. At minimum:

- identifier and metadata bytes;
- Registration and ACK bytes;
- encoded and decoded document bytes;
- chunk bytes and count;
- Registry pages and Catalog live/deleted ZSET page entries and bytes;
- complete Catalog encoded bytes and one Patch's encoded bytes;
- Registration record, complete Catalog Value, and pending-event bytes;
- synchronization event-buffer count, age, and bytes;
- retained Registration recovery-cache age and bytes;
- local view bytes, without a Type or record count ceiling;
- concurrent Redis operations and chunk fetches;
- Redis-command and subscription connections;
- queued wake signals, ACKs, retries, and diagnostics;
- retry delay and concurrency; and
- shutdown time.

Unbounded configuration values are prohibited. Arithmetic uses checked
conversion and checked addition/multiplication before allocation.

## 23. Conformance Requirements

For every normative behavior, the testkit should contain either a byte vector,
state-machine case, Lua vector, or real integration scenario. Fixtures include
both valid and adversarial input.

The shared matrix must cover paginated Registry loads with ordered PING/PONG
fencing, per-Registration register/update/renew/unregister reconciliation,
immutable-TTL enforcement,
explicit-unregister fencing, retained recovery cache, targeted gap repair,
Catalog Hash/ZSET loads and revision ordering, strict-base Catalog Patch,
notification-loss repair, floor fallback, tombstone recovery, last-write-wins
Replace/Delete conflicts,
unbounded-population Registry page traversal with bounded per-operation work,
and Sentinel acknowledged-state loss.

A supported SDK release states:

- protocol versions it reads and writes;
- tested Redis and Sentinel versions;
- cross-language pairs included in qualification; and
- known deviations, if any, that prevent a conformant label.

## 24. Protocol Decisions Still Open

- Freeze the exact language-neutral Attr/Data field-value codec. The Redis and
  Pub/Sub envelope is binary-safe and contains no JSON, but MessagePack per
  application field versus another schema-owned binary codec still requires
  byte vectors and cross-language evidence.
- Benchmark MessagePack event envelopes, full Attr comparison, full Data reset,
  and subscriber fan-out before freezing the event codec.
- Freeze default time and byte bounds for the non-selectable Registration
  recovery cache; `0` duration must disable it.
- Add application-owned Catalog codec vectors as concrete consumers adopt
  scalar, array, map, or schema types. The core intentionally freezes only raw
  field constraints and does not select one universal Catalog type codec.

No implementation detail should become the de facto answer before these items
are explicitly reviewed and reflected in schemas and vectors.
