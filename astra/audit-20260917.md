# Astra 静态审核 (2026-09-17)

审核对象为 HEAD `6e77856` 加当前未提交工作区, 不是仅检查提交差异. 本轮只读取源码、测试和既有回归证据, 未构建、运行测试、下载依赖或修改实现.

重点检查手写 Store/Wheel、配置与类型、Identity/Admission、RpcSession/Runtime、Star/Planet 策略, 并对照 CMake、构建入口及相关测试. 生成代码以 schema、消费接口和上一轮生成一致性结果为依据, 不宣称逐行审计第三方生成器或 gRPC/BoringSSL 内部.

结论: 当前连接骨架和独立存储工具已有较好的正确性基础. 未发现可确认在现有正常调用路径上触发内存损坏的新 P0/P1 问题. 但有历史保留契约不一致、代理接口生命周期陷阱和当前文档方向冲突, 并缺少关键 TTL 性能与端到端数据证据. 以下结论来自静态推演, 未运行新复现用例.

## 1. 应优先处理的问题

### A1 / P2: 空闲时不执行 retention 淘汰

位置: `common/src/store.cpp:125`, `common/src/store.cpp:261`, `common/src/store.hpp:167`.

`retention_` 被定义为历史批次的最长存活时间, 但 `trim()` 仅在写入、有效删除或有到期记录的 tick 提交后调用. 空拍直接返回, `extract()` 和 `snapshot()` 也不处理时间淘汰.

触发顺序: 写入若干长期有效值或删除项, 停止写入超过 retention, 持续调用没有到期项的 `tick()`. 旧历史和相关空节点仍被持有, `extract()` 仍可返回已经超过所述时间窗口的记录. 批次数上限依然有效, 此问题不等于历史数量无限增长, 也不会直接导致重放错序.

建议: 明确采用定期时间淘汰, 在空拍维护路径也处理历史; 或明确把 retention 改为仅提交时执行的惰性策略. 保持整批淘汰和 `oldest_` 的现有包含/排除边界. 历史时间戳目前读取 `Clock::now()`, 测试不能只推进 TTL 的人工时间就声称验证了历史时间窗口.

缺少测试: 纯空闲时间淘汰、时间边界、淘汰后的 stale/相邻游标、墓碑回收后重建, 以及 retention 为零或负值的明确定义.

### A2 / P2: 链式代理返回临时代理的引用

位置: `common/include/astra/proto_proxy.hpp:47`, `common/include/astra/proto_proxy.hpp:327`.

`mutate(msg)` 按值创建代理, 各 setter 返回 `auto&` 指向代理自身. 在同一个完整表达式中链式赋值没有问题, 当前 Admission 的调用属于这种安全用法. 但保留 setter 的返回引用会在分号后悬垂, 即使原 Protobuf 消息依然存活:

```cpp
proto::astra::v1::Ping message;
auto&& edit = astra::mutate(message).request_id(std::uint64_t{1});
// 临时代理已经销毁. 下一次通过 edit 访问代理属于未定义行为.
edit.request_id(std::uint64_t{2});
```

现有注释只要求代理不超过消息寿命, 没有说明返回引用还受代理自身寿命约束. 当前测试均在同一表达式内完成链式操作, 因而没有覆盖此陷阱.

建议: 这种只持有消息引用的小代理可让 setter 按值返回代理副本, 避免新增状态或复杂重载; 若保留引用接口, 应区分左值/右值代理并补全生命周期契约. 所有 Mutator 特化应一起处理. 不将此项说成现有 Admission 已经发生悬垂访问.

### A3 / P2: README 指向另一套 SDK 同步设计

位置: `README.md:33`, `../cluster/key-stream-sync-design.md:3`, `../proto/astra.proto:104`.

README 把按 Key 对账定义为下一阶段方向, 所链接文档仍标为已确认: SDK 提交 Key/Version, 按 Key 补历史, 区分删除与未知. 当前 SyncRequest 草案则使用服务端实例 ID、订阅范围和 Store 提交游标; Store 也明确只提供同实例全范围提取.

两套方向对 SDK 责任、版本含义和恢复规则有实质差异. 这不是已实现网络服务的运行错误, 但会误导后续实现和测试验收, 尤其容易重新引入此次重构希望减少的客户端状态.

建议: 统一当前权威入口, 对旧设计明确标记历史/待重审. 区分 Catalog 发布者业务版本、Registry 所属 Star/注册身份与订阅重放游标. 本轮审核不擅自冻结尚未完成的网络同步协议.

## 2. 性能与精简空间

### O1: 长跨度补拍始终持锁逐拍执行

位置: `common/src/store.cpp:92`.

默认 1ms 间隔下, 暂停一小时对应 360 万拍, 一天对应 8640 万拍. 即使没有有限 TTL 节点, 仍执行这些循环, 并阻塞同 Store 的 put/remove/extract/snapshot. 这些是循环次数, 不是实测耗时.

这是已记录的时间轮使用约束, 不应误报为新发现的轮内链表错误. 不建议为此立即增加多层位图、后台线程或复杂通用调度器. 应先测空轮、稀疏轮及集中到期时的恢复耗时和竞争读写 p99, 再决定是否只在 Store 的大跨度路径重建调度. 正常短间隔热路径优先保持简单.

### O2: 失效快照保留旧载荷直到下一次 snapshot

位置: `common/src/store.cpp:184`, `common/src/store.hpp:182`.

建立大快照并释放外部引用后, 删除全部数据或持续覆盖值; 即使历史已经淘汰, Store 的 `cache_` 仍强引用旧 Map 和旧载荷. 它直到下一次成功构建快照或 Store 销毁才释放. 例如 capacity=0 可以隔离历史影响, 清楚暴露这项额外保留.

这属于失效缓存的内存滞留, 不是无法回收的泄漏. 已返回且仍被读者持有的旧快照必须继续有效. 可评估在成功提交后解除 Store 对失效缓存的强引用, 并把可能很重的最终析构移出状态锁; 不应在每次写入时重建快照.

缺少测试: 用 weak_ptr 检查无外部持有者时的旧载荷释放, 以及仍有读者时的快照隔离. RSS 不一定立即下降, 不适合作为对象已释放的唯一断言.

### O3: 批次数上限不等于内存上限

位置: `common/src/store.hpp:164`, `common/src/store.cpp:214`.

capacity 按完整批次计数, 单次 tick 可以产生很多删除记录; extract 会持锁复制整个后缀中的 Key 和记录数组. 一次大规模集中到期就能形成很大的单批, 即使 capacity=1. 当前 API 已诚实注明这一点, 不是计数实现错误.

业务接入时需要为 Key、载荷、单次响应和在途快照设置实际容量边界. 历史过大可以整批淘汰并回退快照, 不要拆开一个提交后提前确认游标. 优先在明确的服务边界约束输入与输出, 不把内部工具改成庞大通用资源框架.

### O4: 网络控制循环和代理封装的维护成本

- `common/src/runtime.cpp:187` 每轮扫描所有会话, 每次读写回调又会唤醒同一循环. 目前只有低频控制消息, 这种组织方式清楚且可接受. 业务高频推流不能未经测量就沿用全表扫描路径. 先保留现有结构, 后续确有热点再考虑按就绪会话调度.
- `proto_proxy.hpp` 为大量字段手写同构适配, 生产调用目前主要是 RegistrationRequest/Hello. 它提供链式语法, 没有自动消除 Protobuf 分配或复制. 保留代理应有明确维护收益, 尽量收窄到实际使用面, 或由既有生成流程统一维护; 不为它新增运行期反射体系.
- 注释数量已经足够, 应优先纠正事实. 例如 `grpc_session.cpp:276` 写成超时终止进程, 实际关闭的是会话; `grpc_session.cpp:33` 提及 mTLS, 实际服务端明确不请求客户端证书. 大量逐句复述赋值的说明可让位给生命周期、锁、失败原子性和边界原因.

保留已有正确取舍: 单 Store 一把锁、不可变共享载荷、稳定地址 Map 节点、完整批次提交、O(1) 侵入式取消. 不建议为了形式先进而改成无锁容器、每 Key 锁或通用内存池. 早期已测过的节点立即删除、精确存活计数和 append_range 方案不应在没有新证据时重复推动.

## 4. 扩散审查与边界

- Store/Wheel 问题位于 C++ 独立内部库. 检索旧 Rust `cluster/` 和 Go `supervisor/` 未发现对应的 TTL Wheel/提交历史实现. Go `internal/membership/store.go` 是成员持久登记, 不是同一种业务 Store. 当前 Runtime 未接入此 Store, 所以不能说现有网络服务已发生这些数据问题.
- 代理寿命问题影响 C++ 全部 Mutator 特化和未来消费者. 当前 `admission.cpp` 的链式调用在单个表达式内结束, 未发现保存返回引用. Go 生成消息和旧 Rust 消息没有这套借用代理接口.
- 共享协议与文档冲突跨 C++、Go 和未来 Comet SDK 的实现约定, 应统一来源, 不另造一套语言专用语义.
- 旧版 Redis SDK 已退出当前实现方向; 本轮没有重新逐行审核或运行其测试. 上述对应路径检索不等于其他语言全量审计.
