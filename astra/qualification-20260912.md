# C++26 连接骨架补充验收

日期: 2026-09-12. 本报告补齐编译期诊断、关闭契约行为、组网规模和推流成本.
此前的 [2026-09-11 记录](validation.md) 与机器可读历史结果保留, 不把两次测试合并成新的长时运行.
本次没有实现业务存储、Catalog/Registry 复制、Planet 业务重新登记或 SDK 接入.
完整场景、产物/源码摘要、分位数样本和失败历史见 [机器可读结果](../testkit/results/peer-cpp-foundation-20260912.json).
本次普通 Release 的 cluster/planet SHA-256 与此前一小时故障循环的产物一致;
新增语言测试和独立推流目标不改变这两个生产程序, 因此沿用该长时证据, 没有重复启动一小时测试.

## 语言与行为边界

- 真实 CLI 元数据有一个编译正例及七个编译负例: 重名、缺注解、空说明、反向范围、非法默认值、
  不支持类型、注解容量超限. 先验证正例, 再要求负例命中对应诊断, 不接受任意编译失败.
- 独立进程检查正常调用、契约违例、STL 越界. 违例要求对应诊断及 SIGABRT, 禁止 core dump.
- `--contracts ignore` 使用独立 Release 目录. 六组 CTest、八组 RPC/跨语言场景、十三组进程场景通过,
  证明外部输入验证、认证和恢复行为不依赖契约启用. 默认仍为 enforce, 不支持 assume.
- Windows 现有 clang-tidy 22.1.3 拒绝 `-freflection`, 也不能解析 `template for`;
  Ubuntu 未安装 clang-tidy. 因此没有声称 C++26 clang-tidy 全量通过. 严格 GCC 警告、源码审查和 sanitizer 各自保留.

验证 Planet 切换和剩余 Star 全互联, 再重启同端点并确认新 UUID 和完整组网. 所有组的进程、端口和临时目录清理通过.

正常关闭时间包含进程退出及 reader join, 未拆成每个内部回调的取消到 OnDone 延迟.
两方向 Star 全互联的流数按 N*(N-1) 增长, 规模成本不能因为采用 gRPC 而忽略.

数据是累计成功分配的请求次数和字节, 不是活跃对象数、RSS 或最大占用. 它们不混入上面的普通构建计时.

## 隔离推流方法

使用既有 `testkit/transport/proto/probe.proto` 和共同的 Rust 接收器. 不修改生产 SessionPacket.
每个接收器检查连续 revision、键规则、完整接收数量、最终缓存摘要及稀疏确认计数.
完成水位还必须等于计划源更新数加已接受发布请求数, 不能用自洽但提前结束的流蒙混通过.

- Rust Tonic, C++ 普通 Protobuf 对象, C++ 有界普通对象复用三组; 没有 Arena 或共享序列化.
- 两个可用 CPU 的进程亲和性, TLS 1.3, 32 KiB 消息上限, 初始 65,535 字节窗口, 关闭自适应增长,
  512 条广播环、16 条出站队列预算、8 条控制队列预算. gRPC/Tonic 的内部调度与缓冲实现仍然不同.
- Registry 数量 100/1000/10000; Catalog 正文 64/256/1024 bytes; 扇出 1/4/16;
  均匀/16 热点键、稳态/50 ms 突发、200 ms/1000 ms 暂停消费. 每端额外 20 Ping/s、5 小发布请求/s.
- 每个场景/实现独立预热 0.5 秒, 正式五轮交错重复, 每轮发压两秒. 分位数保留每次统计,
  汇总中使用五次结果的中位数, 不宣称这是合并后的总体 p99.
- 更新延迟由发布端计划时间到该端收到应用累计水位确认计算, 每 128 条抽样, 使用 100 us 桶.
  包含调度落后和排队, 不是单向网络延迟. 每端分位数取最差端, 同时保存原始样本数和过期/跳过数.
  例如 2,000 次/秒、两秒一轮仅约 31 个水位样本/接收端, p99 很接近该轮最大样本;
  五次交错重复便于发现持续差异, 仍不足以对生产尾延迟作高置信度承诺.
- 接收 Protobuf 编码字节不含 TLS、HTTP2 和 gRPC 前缀开销, 与业务正文字节分列.
- 广播环溢出是容量拒绝, 保留失败次数和原因, 不把不完整流填入成功吞吐/延迟平均值.
  超预算的整个试验没有完整接收计数时明确记为 unknown, 不伪造零丢失.

这里比较两套实现和不同对象所有权策略. Rust Bytes 共享正文, C++ 普通消息复制正文;
两者并非相同分配器、TLS 实现或线程调度器, 不能把差值直接解释成语言本身性能差异.
两秒发压也不足以认定最大持续吞吐或生产容量.
本轮 reuse 复用每个队列槽的 Event 外层对象; 生成的 Event::CopyFrom 会 Clear 其 oneof,
因此不会自动保留内部 Update 对象及正文容量. 这不等价于 Arena、持久 Update 缓冲或完全消除分配,
也解释了为什么不能只看到“复用”选项就推定会有显著性能收益.

## 本轮发现和扩散审查

1. 新增 C++ 推流 Reactor 在处理入站请求时可能间接再次触发读取, 已用 processing_read_ 保持接收对象独占.
   生产 C++ Session 已有上一轮验证过的 read_ready_ 交接保护; Rust 使用独立拥有的消息顺序读取;
   Go Supervisor 为 unary 请求, SDK 未复用此 Reactor, 没有同一路径.
2. 既有 Rust 测试接收器漏处理合法 Rejected 发布应答. ASan 下实际出现源结束后的在途发布被拒绝,
   修复后单独计数拒绝, 仍校验请求关联和最终水位. C++/Rust 发布端原本都返回拒绝, 不需改生产代码.
   增加确定性晚到发布测试. Go Supervisor 和 SDK 没有该实验协议; 不把它们列为已复现.
3. 旧基准报告写死的 1 MiB 窗口与本次实现配置不一致, 已修正当前报告生成器.
   历史 2026-09-10 报告仍对应当时的 1 MiB, 不回写历史结果或混合比较.
4. C++ 构建入口将第三方 lib 目录放入了所有子进程的 LD_LIBRARY_PATH. 完整 TSan 前缀恰好也有共享 zlib,
   Rust/LLVM 加载它后使未插桩编译器混入 libtsan, 在 fork 阶段崩溃. ldd 验证原因后移除这个不必要的搜索目录,
   只保留 GCC 运行库目录. 服务和 protoc/plugin 的第三方依赖均已静态链接, 没有改用未插桩库规避检查.
   Rust/Go 自身入口没有注入该路径; 影响来自 C++ 测试入口启动其它语言工具, SDK 未修改.

C++ 普通对象在本机约 80k 次交付/秒仍可完成, 但高压下尾延迟和 CPU 成本显著高于此 Rust 实现.
因此本次结果支持 C++ 连接骨架可用, 不支持“改为 C++ 就会更快”的结论.
若未来业务要求低毫秒尾延迟且高扇出, 应以真实生产数据通路重新验收, 不能直接沿用本夹具的速率.

首次 C++ 逐条刷新基线在 207/225 个试验后出现一次未解释 Closed 流错误, 此前大量高扇出/8k 场景触发容量拒绝.
其完整失败记录保留, 不能称为五轮通过. 新版只对已经就绪的更新使用公开 WriteOptions 缓冲提示,
最多 16 条, 控制应答与尾条立即刷新. 新版完成了上述 225 个试验且常规场景全部通过.
这提供了采用小范围批量刷新的证据, 但没有独立复现旧 Closed 的内部原因, 不声称定位并修复了它的全部根因.
该策略留在隔离夹具; 生产骨架只有控制消息, 没有将业务优化硬塞入当前 SessionPacket.

## 补充安全检查

最终批量夹具的 ASan/UBSan 与完整 TSan 各完成六组 CTest 和 12 个推流组合, 没有增加 suppressions.
TSan 每秒 2,000 次发压会触发广播环上限, 对正确性冒烟降到明确记录的 200 次/秒;
ASan 与普通冒烟保持 2,000 次/秒. 低速 TSan 不充当性能或最大容量证据.
库搜索路径修复后完整 TSan 的八组 RPC/跨语言场景、十三组进程场景再次通过, 清理通过.

## 推流分配与采用决定

独立计数构建的四个场景、两种 C++ 模式各跑五轮, 40/40 通过并正常退出输出计数.
下表是每进程完整生命期成功 C++ new 请求的中位数, 包括预置数据、认证和退出前的库活动:

| 场景 | fresh 次数 / 请求字节 | Event reuse 次数 / 请求字节 |
| --- | ---: | ---: |
| 混合 | 318,360 / 31,377,116 | 302,074 / 30,597,600 |
| 10,000 Registry 热点 | 345,380 / 33,701,216 | 329,083 / 32,918,949 |

保留公开批量写 API 的实验和可重复对照, 业务同步阶段再针对实际消息类型决定是否复用内部 Update 对象.

## 当前入口与完成边界

默认入口为 Linux C++26 Star/Planet 与 Go Supervisor, Rust 保留显式对照及跨语言验证用途:

```bash
bash scripts/test-services.sh
bash scripts/test-services.sh --mode soak --duration 3600
bash scripts/test-services.sh --implementation=rust
```

Windows 使用 `scripts/test-services.ps1 -Implementation rust` 运行 Rust 对照;
默认 C++ 选择明确报告需要 Linux, 不静默回退. 独立 `cluster-cpp/build.sh` 可选 Debug、Release、ASan、TSan,
关闭契约和分配模式使用不同目录, 普通构建不下载依赖、不生成协议、不改变全局配置.

第一阶段的连接、角色、生命周期、语言诊断、兼容、资源及性能证据已经具备.
默认 Linux 一键入口已通过生成核对、六组 CTest、Go vet/测试/race、八组 RPC/互通和十三组进程回归.
Python 编排器 Windows 31 项通过, Linux 30 项通过及 1 项平台跳过; 改动的 Rust 夹具两端各 16 项及 Clippy 通过.
测试持有进程均已退出, 监听端口可复用, 临时目录已清理. 本轮没有继续后台长时运行.
